# 02 · 架构与运行时调用链

> 目标：搞清"敲下 `flexible-factory run` 之后，代码按什么顺序跑了哪些东西"，以及"为什么这么分层"。
> 主要依据：`src/flexible_factory/` 各模块 docstring、`PROJECT_ENGINEERING_REFERENCE.md` 第 2 节、`application/coordinator.py` 模块说明。

## 1. 五层架构

```text
┌──────────────────────────────────────────────────────────────┐
│  cli.py                       唯一命令入口（argparse）        │
├──────────────────────────────────────────────────────────────┤
│  application/                 用例编排：生命周期、运行、协调器 │
│                               批次、目录、订单、planner、报告  │
├──────────────────────────────────────────────────────────────┤
│  domain/        纯业务逻辑     │  simulation/      仿真与设备   │
│  规则/物料/任务/资源/指标      │  场景/布局/物理/运动/AGV/控制器│
│  工艺目录/工序图/调度/订单     │  execution/ 执行适配器         │
├──────────────────────────────────────────────────────────────┤
│  artifacts/     场景工件与迁移  │  persistence/  数据库与仓储   │
├──────────────────────────────────────────────────────────────┤
│  api/           本地 HTTP 适配器（只做传输）                   │
└──────────────────────────────────────────────────────────────┘
        frontend/ 独立 React 工作台（只消费 /api，不碰仿真）
```

### 1.1 依赖规则（硬约束，代码里有测试守着）

```text
cli → application → domain / simulation / artifacts / persistence

domain      ── 只允许导入 domain.rules 和 spec；禁止 CoppeliaSim / SQLAlchemy / 文件系统
simulation  ── 禁止导入 application / cli
persistence ── 只允许 domain / util / SQLAlchemy；禁止 simulation / application / cli
artifacts   ── 负责 manifest 与工件；场景对象校验委托给 simulation.contract
api         ── 只做 JSON 编解码 + 路由 + 错误映射，不持 sim/scene/handle
```

为什么值得较真：

- `domain` 不依赖仿真器 → 62 个测试文件里绝大多数**不需要 CoppeliaSim**，1 秒级跑完；
- `persistence` 不依赖 `simulation` → ORM 对象不会泄漏到业务层，仓储返回的是领域数据类；
- 边界有测试：`tests/test_v1_import_boundary.py`、`tests/test_v1_execution_boundary.py`、`tests/test_v1_controller_module_layout.py`。**改 import 前先看这几个测试，它们会直接失败。**

### 1.2 模块职责速查

| 包 | 文件数 | 职责 | 一句话记忆 |
|---|---|---|---|
| `domain/` | 14 | 规则、物料、任务、资源、指标、工艺目录、工序图、调度、订单（校验/编译/失败） | "不碰仿真器的业务大脑" |
| `simulation/` | 28 + `motion/`15 + `execution/`4 | 配置、场景构建、布局、物理、传送带、AGV、UR5 IK、控制器、运动规划、执行适配 | "所有会碰 CoppeliaSim 的东西" |
| `application/` | 11 | 生命周期、run、协调器、批次、目录、订单服务、planner、报告 | "把大脑和身体连起来的用例层" |

## 2. CLI 命令地图

`cli.py` 797 行，全部命令挂在 `build_parser()`（:465）。按用途分四组：

### 用户命令（开仿真器才用）

| 命令 | 作用 | 关键点 |
|---|---|---|
| `list` | 列出工件 | 只读目录 |
| `status` | 生命周期状态 | `--offline` 不连仿真器 |
| `load` | 加载 `current.json` 指向的工件 | **不 build、不清场** |
| `validate` | 只读校验 | 可选诊断，不是 run 的前置 |
| `stop` | 停止并确认停止态 | 释放普通锁，**不清安全锁存** |
| `run` | 跑 `full_flow` | `cmd_run` 在 :413 |

### 维护命令（开仿真器）

| 命令 | 作用 |
|---|---|
| `migrate` | 从 stage4 工件只读派生 v1 工件（幂等） |
| `build` | 从 stage3 父场景构建 v1（`--save` 才落工件） |

### 数据命令（**不需要**仿真器）

| 命令组 | 子命令 | 作用 |
|---|---|---|
| `catalog` | `init / import / publish / status / diff / verify` | 静态工艺目录 → SQLite |
| `knowledge` | `import / publish / status / verify` | Neo4j 导出 JSON → SQLite |
| `report` | `runs / run / genealogy / waits / timeline` | Q1–Q4 运行记录查询 |
| `order` | `validate / create / version / list / show / preview / plan / start / status / nodes / events / runs / stop` | 订单 DAG |
| `api` | `serve` | 本地 HTTP 服务（8080） |

### 退出码约定（写脚本时有用）

| 码 | 含义 |
|---|---|
| 0 | 成功（或报告 `all_ok: true`） |
| 1 | 运行完成但验收失败（`all_ok: false`） |
| 2 | 前置条件错误（`LifecycleError`/`ArtifactError`/`BatchError`/`CatalogPersistenceError`） |
| 3 | 校验失败（`ValidationFailedError`/订单 spec 校验/planner 错误） |

## 3. `run` 的完整调用链（15 步）

以 `flexible-factory run --scenario full_flow --time 700` 为例，按时间顺序：

```text
 1. cli.main()                                   cli.py:770
 2. build_parser() → cmd_run(ns)                 cli.py:465 → :413
 3. resolve_batch(scenario, profile)             application/batch.py
       └ 批次在"连仿真、取锁"之前校验，非法直接退出
 4. [仅 --catalog-source db] runtime_catalog()   application/catalog.py
       └ 必须与代码默认目录逐字段等价，否则连仿真器都不连就拒绝
 5. setup_logger(--log)                          application/run.py:50
 6. _connect(host, port)                         simulation/component_builder.py:40
       └ 建立 ZMQ Remote API 连接，拿到 sim / simIK
 7. LifecycleManager.load(artifact)              application/lifecycle.py:609
       └ 加载 current.json 指向的 scene.ttt，读 manifest，进入 SCENE_LOADED
 8. manager.prepare_start(target="full_flow")     lifecycle.py:873
       └ 取运行锁（冲突 → RUN_CONFLICT）+ 启动点全量校验（失败 → 退出码 3）
       └ 返回 run_id，状态进入 SIMULATION_RUNNING
 9. run_loaded_scene_v1(...)                     application/run.py:296
10. build_components_v1(...)                     run.py:60
       └ 共享组件 + 5 台 IK + 5 台吸盘 + 影子臂/碰撞集合（build_v1_runtime）
       └ 物料账本 MaterialRegistry
11. 写 v1_scene_snapshot_<stamp>.json             run.py:359
12. start_stepping(sim) + probe_conveyor_drive()  component_builder.py:81 / :274
       └ 必须 setStepping(True)：之后 Python 每步只 sim.step() 一次
13. run_scenario_v1(...)                          run.py:195
       └ Stage4Coordinator(...).start() 然后 while not finished: coordinator.step()
       └ 每步检查 stop_event / pause / 仿真时间上限 / 墙钟上限
14. 收尾：stop_simulation() + runtime.destroy()    run.py:408
       └ **必须**在停止态销毁 Shadow_* 影子对象，否则工件会被污染
15. finish_run() + 写 v1_run_<scenario>_<stamp>.json  run.py:418
       └ all_ok 决定退出码 0 还是 1
```

两个"必须记住"的细节：

- **第 8 步的锁**：`prepare_start` 先取运行锁再校验。所以两个人同时跑会得到 `RUN_CONFLICT`，而不是场景被踩坏。
- **第 14 步的顺序**：`stopSimulation()` → 销毁影子臂/碰撞集合。反过来做会让句柄失效，`runtime_destroy` 报错。

## 4. 单步 `step()` 的 8 个阶段

`application/coordinator.py:227`。这是整个项目**唯一的 `sim.step()` 调用点**，也是理解调度的关键。

```text
def step():
  1. _poll_sources()          来源生成：区域未满、间隔够、批次还有余量 → 生成物料
  2. _poll_tasks()            任务轮询：ready 实例 → 调度决策 → 申请资源 → 启动执行
       ├ _dispatch_ready()    调 domain/scheduling.py 的纯策略选设备，记录候选与理由
       ├ _poll_unit()         臂任务：全量申请资源 → start_unit_task
       └ _poll_agv()          AGV 任务：航线规划 → 申请直道/dock → launch_route
  3. _maybe_inject_fault()    故障注入（agv_blocked / conveyor_stop），只在指定 scenario 生效
  4. executor.pre_tick()      所有活动臂执行器：把控制器推进一帧（算关节目标，不动仿真）
  5. _advance_route()         AGV 航线 pre_tick：算轮速
  6. sim.step()               ★ 唯一一次推进仿真（dt = SIM_STEP = 0.05 s）
  7. executor.post_tick()     步后联锁：安全检查、吸附/释放确认
  8. _after_step()            读状态 → 完成校验 → 物料提交 → 配对 → 释放资源 → 记指标
       └ _timeout_check()     超时 / 背压超时 / 稳定性检查 → 冻结或失败
```

**为什么必须"唯一步进点"**：

- Python 是时钟主控（clock master）。`setStepping(True)` 之后，CoppeliaSim 只在收到 `sim.step()` 时前进 0.05 s；
- 如果控制器里也调 `sim.step()`，一步就会变成两步甚至更多，所有实测的时间/距离/容差全部失真；
- 所以 `simulation/execution/*` 明确"**不调用 sim.step()**"，`unit_controller` 只被 `pre_tick` 驱动。这条边界有测试守着（`test_v1_execution_boundary.py`）。

## 5. 生命周期状态机

`application/lifecycle.py:73` 的 6 个状态，`:82` 的迁移表：

```text
                 connect                build                 save
DISCONNECTED ──────────► CONNECTED_STOPPED ──────► SCENE_VALIDATED ──► SCENE_VALIDATED
                              │  load                    ▲   │
                              ▼                          │   │ start
                         SCENE_LOADED ──── validate ─────┘   ▼
                              │                        SIMULATION_RUNNING
                              └──────── start ───────────────► │
                                                               │ stop
                              SCENE_VALIDATED ◄────────────────┘
```

要点：

- **`start` 不会隐式 `build`/`clear`**。这是刻意的：一旦允许"启动时顺手重建"，就永远说不清跑的是哪个场景。
- **运行中拒绝** `build/load/save/validate/start`（会抛 `INVALID_STATE`）。
- `ERROR` 状态可以 `connect/build/load` 恢复，但不会自动回到运行态。

## 6. 三种执行模式

| 维度 | recipe 模式（`run`） | order 模式（`order start` / `api`） | planner 模式 |
|---|---|---|---|
| 谁决定做什么 | 固定配方 + 批次（`SCENARIO_BATCH`） | 用户写的 `OrderSpec`（DAG） | planner 从目标物料反推草稿 |
| 入口 | `run_loaded_scene_v1` | `OrderSimulationWorker` → runner | `OrderService.plan()` → 存草稿 |
| 工序图来源 | `OperationGraph(recipe=...)` | `OperationGraph(order=...)` | 编译后的同一张图 |
| 校验 | 目录校验 + 批次校验 | 结构校验 + 端口校验 + 目录校验 + 编译 | 同 order，加上搜索上限 |
| 需要仿真器 | 是 | 是（`start`）；`preview` 不需要 | **不需要** |
| 代码入口 | `run.py:296` | `application/orders.py:244` / `order_runner.py:53` | `application/planner.py` |

三者**共用** `OperationInstance` / `OperationGraph` / `OperationRuntime` 的 ready→commit 生命周期。这是阶段 3 最重要的重构：把"任务链"从模板的 `successors` 静态推进，改成"实例图 + ready 集合"驱动。

## 7. 六个关键设计决策（面试/答辩可以直接讲）

### 7.1 Python 是唯一时钟主控

`setStepping(True)` + 每步一次 `sim.step()` + `SIM_STEP=0.05`。好处：Python 侧的规划和物理侧的状态严格同步；坏处：必须自己管"步内顺序"，所以 `step()` 的 8 个阶段不能乱。

### 7.2 资源"全有或全无"

`ResourceTable.acquire_all()`。好处：不会死锁、不会部分持有；坏处：可能"明明只差一个 dock 就能开工"却要等整组资源。项目选了简单可证明的一边。

### 7.3 提交边界唯一

`_commit_operation()` / `_commit_unit_result()` 是**唯一**的"成功"边界：执行器说 `SUCCEEDED` 只代表"动作做完了"，物料是否真的到位、类型是否转换、区域容量是否允许，要应用层再验一遍。这条区分在 `execution/base.py` 的 docstring 里写得很清楚。

### 7.4 工件不可变 + 摘要校验

`protected: true` + 文件只读 + manifest 里存 `config.digest` 和 `scene_sha256`。任何"运行结果对不上"的情况，先怀疑工件被改动过。

### 7.5 执行适配器与调度分离

`simulation/execution/` 只做 `start/pre_tick/post_tick/poll`，**不含调度策略**。这样"换一个 AGV 控制器"不需要动协调器；"改调度规则"不需要动控制器。

### 7.6 失败分类是 allowlist，不是"看情况"

`domain/failures.py:117 classify_failure`：只有 `NODE_PRECHECK_REJECTED`（物理动作前、物料可核实、资源已释放）才允许标记为 NODE（只阻断依赖后继）；安全锁存、仿真基础设施、共享资源、未知异常**一律 GLOBAL**（整个运行 ABORTED）。

宁可"误杀"整个运行，也不要把"其实设备已经撞了"说成"只是一个节点失败"。这个保守取向贯穿全项目。

## 8. 读代码时的 8 个坑

| # | 坑 | 真相 |
|---|---|---|
| 1 | 以为 `Stage3*`/`Stage4*` 是两套代码 | 是**同一继承链**的层名（base → motion → dual → uflow），类名保留是因为契约/工件里引用了它们 |
| 2 | 以为 `unit_controller_dual.py` 是独立实现 | 只有 0.6 KB，纯 re-export 兼容层 |
| 3 | 以为 `runtime.py` 只有 v1 | 同时有 `build_stage3_runtime()` 和 `build_v1_runtime()` |
| 4 | 以为 `coordinator` 会写机械臂位姿 | 不会，它只下命令 + 校验结果；位姿由控制器算 |
| 5 | 以为 `executor.poll() == 任务成功` | 不等于，还要过应用层校验（见 7.3） |
| 6 | 以为 `--scenario no_pair` 是产品功能 | 只是内部回归；用户模式只有 `full_flow` |
| 7 | 以为改 `config.py` 无所谓 | 它参与 `config_digest`，改了受保护工件的校验就失败（要么新工件，要么别改） |
| 8 | 以为 `docs/implementation/runs/` 里的 JSON 是证据 | 不是，那是**临时运行输出**，正式证据在 `evidence/`，且被报告引用 |

另外三个"文档级"的坑：

- `config_base` / `config_motion` / `config_dual` / `config` 四个配置**不是并列的四份**，是四层叠加：后一层 import 前一层，v1 只加自己的参数；
- `motion/path_planning.py` 是兼容导出层，真正的实现在 `plan_types/plan_checks/plan_search/plan_postprocess`；
- `PROCESS_MODEL_VERSION` 变了，说明工艺语义变了；`SCENE_CONTRACT_VERSION` 变了，说明场景对象变了。**两者不能混着改**。
