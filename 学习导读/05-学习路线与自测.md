## 3. 20 道自测题

先自己答，再对下面的"答案要点"。答不上来的，回对应篇章。

**Q1.** 为什么必须由 Python 做时钟主控，而不是让 CoppeliaSim 自己跑？
**Q2.** `SIM_STEP` 是多少？为什么"每步只能调一次 `sim.step()`"？
**Q3.** 8 种物料类型里，哪两种是"半成品"？它们分别在哪台臂上产生？
**Q4.** `SEMI_AB` 和 `SEMI_AC` 的区别是什么？
**Q5.** `housing_finish` 的前驱策略是 `any`，为什么不能是 `all`？
**Q6.** `kit_join` 为什么不是 `Stage4Task`？
**Q7.** 工艺目录校验会拦住哪五类错误？
**Q8.** 资源表为什么要求"全有或全无"？代价是什么？
**Q9.** `zone_ab` 和 `zone_ac` 是什么？为什么会有这两个资源？
**Q10.** 调度排序的四个键是什么？为什么最后要用"稳定实例 ID"？
**Q11.** `run` 为什么要"先取锁再校验"，而不是反过来？
**Q12.** 为什么批次要在"连仿真器之前"校验？
**Q13.** 说出单步 8 个阶段，并指出哪一步是唯一的 `sim.step()`。
**Q14.** 执行器返回 `SUCCEEDED` 之后，为什么还要应用层再验一次？
**Q15.** `simulation/execution/` 为什么不允许调用 `sim.step()`？有测试守着吗？
**Q16.** `config_digest` 是怎么算的？改了 `config_motion.py` 的一个容差会发生什么？
**Q17.** `current.json` 里为什么要存 `manifest_digest` 和 `scene_sha256`？
**Q18.** 订单为什么"只能追加版本，不能改"？靠什么技术手段保证？
**Q19.** planner 为什么只把"已登记路线"当 macro，而不自由拼单工序？
**Q20.** 怎么判断一个"能力"是真实实现，而不是计划？

### 答案要点

| # | 要点 |
|---|---|
| Q1 | 为了让 Python 侧的规划/决策与物理状态严格同步（每步 0.05 s 确定性推进）；否则仿真器按自己的实时/固定步长跑，外部控制拿到的状态是"过期"的 |
| Q2 | `0.05 s`（`config_base.py:25`）。多次 step 会让一步变成多步，所有基于时间/距离的容差、节拍、实测数字全部失真 |
| Q3 | `SEMI_AB`（B 臂产生，在 AGV 上）、`SEMI_AC`（A 臂产生，在 A→C 交接台） |
| Q4 | `SEMI_AB` 是"B 加工完、还没回到 A"的中间态；`SEMI_AC` 是"A 段完成、可以进 C"的状态。`PROCESS_TRANSITIONS` 里 `(A, SEMI_AB) → SEMI_AC` 就是这个转换 |
| Q5 | 壳体有直达和绕行两条互斥路线，实际只会走其中一条；用 `all` 会永远等另一条不存在的路线，任务永远不 ready |
| Q6 | 它是纯逻辑合流（`physical=False`、不占资源、无运动），由 `_check_join()` 在两条输入都提交后建节点并调 `commit_join()` |
| Q7 | 未知设备/区域/资源、重复 ID、缺失端口、无效后继、循环依赖（`ProcessCatalog.validate()`） |
| Q8 | 避免死锁和"部分持有"（拿着 dock 等臂，别人也用不了）；代价是可能出现"只差一个资源却要等整组"的低效 |
| Q9 | A/B 臂、A/C 臂的包络互锁区（基座间距 < 2×臂展）。相邻臂不能同时运动，否则会撞 |
| Q10 | 业务优先级 → 等待时长 → ready 时间 → 稳定实例 ID。最后一项保证"完全同条件时结果确定"，让测试可复现 |
| Q11 | 先取锁能保证"校验期间场景不会被别人加载/构建/运行"；反过来会给"校验通过但场景已被改"留下窗口 |
| Q12 | 非法批次不该消耗仿真资源和运行锁；`cmd_run` 第一行就 `resolve_batch()` |
| Q13 | 来源生成 → 任务轮询 → 故障注入 → `pre_tick` → AGV 航线 → **`sim.step()`** → `post_tick` → `_after_step` |
| Q14 | `SUCCEEDED` 只代表"动作执行端完成"，物料是否到位、类型是否转换、区域是否允许，要应用层校验后才提交（唯一成功边界） |
| Q15 | 因为唯一步进点在协调器；适配器 step 会导致一步多推。有 `tests/test_v1_execution_boundary.py` 守着 |
| Q16 | 由四层配置的可序列化常量算出（排除 `MODEL_BASE`、`DEFAULT_LOG_FILE`）。改了容差 → digest 变 → 旧工件 `validate` 失败 → 必须新建工件或改回去 |
| Q17 | 让"指针指向的东西"可验证：manifest 摘要防 manifest 被改，scene sha256 防场景被换。只存路径的话，被掉包也发现不了 |
| Q18 | 正在跑的实例绑定了具体版本；改版本会让在跑的运行对不上号。技术手段：只能 INSERT 新行 + 数据库触发器禁止 `order_version` UPDATE |
| Q19 | 单工序拼边会跳过 AGV 运输等中间工序，产生"看起来连通、实际不可执行"的图；只拼已验证的路线 macro 能保证可执行性 |
| Q20 | 看三样：①代码里有没有真实执行路径（不是 TODO/文档）；②`docs/implementation/evidence/` 有没有对应 JSON；③报告里有没有写明执行时间与结论。缺一按"计划"算 |

## 4. 五个安全实验

都不需要 CoppeliaSim 也能做前四个。

### 实验 1：跑纯逻辑回归，看"哪些行为被锁住了"

```powershell
python -m pytest -q
python -m pytest -q tests/test_v1_process_model.py -v      # 看每个测试名 = 一条规则
```

**看什么**：测试名是不是像"规则清单"？这就是这个项目的规格说明书。

### 实验 2：核对工件没被改过（1 分钟，很有成就感）

```powershell
$p = "docs/scene_artifacts/v1/L5_UFLOW/v001_20261103_004317/scene.ttt"
(Get-FileHash $p -Algorithm SHA256).Hash.ToLower()
# 期望：bf7e4df6681abf8027e3f04e3bb214fc5a1f707d1be8922a733fce424a2a352c
```

再对比 `manifest.json` 的 `artifact.sha256` 和 `current.json` 的 `scene_sha256`——三处必须一致。

> 小发现：这个迁移工件的**文件属性其实是可写的**（`IsReadOnly = False`）。保护主要靠 `manifest.protected = true` + `ArtifactStore.check_writable()` + 摘要校验，不是文件系统 ACL。所以"别用 GUI 保存覆盖"是纪律，不是系统拦得住。

### 实验 3：读一份运行报告，只看顶层

```powershell
$f = Get-ChildItem docs/implementation/runs/v1_run_full_flow_*.json | Sort-Object LastWriteTime -Descending | Select-Object -First 1
(Get-Content $f -Raw | ConvertFrom-Json).PSObject.Properties.Name
```

**看什么**：`scenario` / `fault` / `batch` / `batch_profile` / `catalog_source` / `results` / `run_record` / `all_ok` / `runtime_destroy`。再往里看 `results[0].acceptance` 的验收项。

### 实验 4：把工艺目录写进数据库再对比

```powershell
flexible-factory catalog init
flexible-factory catalog import            # 记下返回的 release_id
flexible-factory catalog publish --release-id <release_id>
flexible-factory catalog diff              # 必须 "ok": true
```

**看什么**：`diff` 为空说明"代码目录"和"数据库目录"逐字段等价——这是 `--catalog-source db` 的前置条件。

### 实验 5（需要 CoppeliaSim）：跑一次 `full_flow` 并对比报告

```powershell
flexible-factory load
flexible-factory run --scenario full_flow --time 700
```

**看什么**：`docs/implementation/runs/` 新增的 JSON 里 `all_ok`、FINAL 数量、`runtime_destroy`（有没有残留 `Shadow_*`）、运行记录是否写入。

## 5. 如果要答辩/汇报，背这五句

1. **它是什么**：用 Python 通过 ZMQ 远程控制 CoppeliaSim 4.10 的五岛柔性车间，两种原料经三条路线在 E 岛配对成一个成品。
2. **它的难点**：不是动作，是调度——资源互斥、背压、故障冻结，全项目最厚的是 2625 行的协调器。
3. **它的架构**：domain 纯逻辑 / simulation 碰仿真 / application 编排 / artifacts 工件 / persistence 数据，依赖单向，边界有测试。
4. **它的严谨处**：唯一 `sim.step()`、全有或全无资源、唯一提交边界、不可变工件 + 摘要校验、失败分类是保守 allowlist。
5. **它的边界**：已实机验收的是 full_flow / 批次 / 调度 / 订单阶段 6；**未验证**的是真实运动故障的 NODE 准入、自动恢复、多订单并行。别把计划说成能力。
