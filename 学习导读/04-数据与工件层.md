# 04 · 数据与工件层

> 目标：搞清"场景、配置、运行结果、订单、知识"这五类数据分别存在哪、为什么这么存、怎么查。
> 主要依据：`artifacts/store.py`、`persistence/*`、`docs/scene_artifacts/README.md`、`docs/implementation/reports/data-platform/*.md`。

## 1. 三类数据，三个地方

| 数据类型 | 存放位置 | 格式 | 能不能手改 |
|---|---|---|---|
| **场景本体** | `docs/scene_artifacts/v1/L5_UFLOW/<版本>/scene.ttt` | CoppeliaSim 二进制场景 | ❌ 绝对不能（只读 + 摘要校验） |
| **场景元数据** | 同目录 `manifest.json` / `validation.json` / `lifecycle.jsonl` | JSON / JSONL | ❌ 不能（改了摘要对不上） |
| **运行输出** | `docs/implementation/runs/v1_run_*.json` | JSON（大，17 MB 级） | ✅ 可以删（临时输出，不是证据） |
| **结构化数据** | `var/catalog/catalog.db`（SQLite） | 目录 + 知识图谱 + 运行记录 + 订单 | ⚠️ 用命令改，别直接 UPDATE |
| **正式证据** | `docs/implementation/evidence/*.json` | 精简 JSON 摘要 | ❌ 归档后不改 |
| **日志** | `flexible_factory.log` | 文本（每次追加） | ✅ 可删 |

一句话记忆：**`scene_artifacts` 是"版本库"，`catalog.db` 是"数据库"，`runs/` 是"草稿纸"，`evidence/` 是"盖章件"。**

## 2. 场景工件（artifact）解剖

```text
docs/scene_artifacts/
├── v1/
│   ├── current.json                     ← 指针：当前用哪个版本
│   └── L5_UFLOW/
│       └── v001_20261103_004317/        ← 一个不可变版本
│           ├── scene.ttt                ← 2.7 MB 场景本体
│           ├── manifest.json            ← 222 KB 身份+体检报告
│           ├── validation.json          ← 58 KB 迁移时的只读校验（452 项）
│           └── lifecycle.jsonl          ← 每次 load/start/stop 追加一行
├── stage3/L2_MIRROR/v008_.../           ← 只读迁移来源
└── stage4/L5_UFLOW/v004_.../            ← 只读迁移来源
```

### 2.1 `current.json`（7 行，但很重要）

```json
{
  "artifact_id": "v1/L5_UFLOW/v001_20261103_004317",
  "path": "L5_UFLOW/v001_20261103_004317",
  "manifest_digest": "1bc46e1b...",
  "scene_sha256": "bf7e4df6...",
  "updated_at": "2026-11-03T00:46:35+08:00"
}
```

- 这是**唯一指针**，其他文档不许另存副本；
- 只在"新工件写入 + 重新加载 + 只读校验通过"后**原子更新**；
- `manifest_digest` + `scene_sha256` 让你能验证"指针指向的东西没被换掉"。

### 2.2 manifest.json 的 22 个顶层键

| 键 | 作用 | 举例 |
|---|---|---|
| `schema_version` | manifest 结构版本 | `"2.0"` |
| `artifact_id` | 版本标识 | `v1/L5_UFLOW/v001_20261103_004317` |
| `created_at` | 创建时间 | `2026-11-03T00:44:49+08:00` |
| `source_phase` | 来自哪一层 | `"v1"` |
| `protected` | 是否受保护 | `true` |
| `parent_artifact` | 来源追溯（含 stage4 摘要 + 再上一级 stage3） | 见下 |
| `code` | 生成时的 git commit/branch/dirty 状态 | `dirty: true` + 改动文件清单 |
| `config` | **配置摘要**（`digest` + `summary`） | 全项目最关键的校验字段 |
| `simulator` | CoppeliaSim 版本、引擎、步长 | `4.10.0.0` |
| `models` | 用到的内置模型清单 + 路径 + 尺寸 | UR5 / suction pad / conveyor / p3dx |
| `layout` | 布局摘要（五岛坐标、线、dock） | 与 `layout.py` 对应 |
| `objects` | 全部对象（alias、类型、父子、位姿） | 受保护对象清单 |
| `geometry` | 拓扑摘要（链、包围盒） | 构建契约证据 |
| `tool` | 工具几何（TCP、吸盘半径） | 抓取标定依据 |
| `physics` | 物理参数（static/respondable/质量/摩擦） | |
| `scripts` | 脚本策略（剥离了哪些 child script） | 4.10 兼容的关键 |
| `builder` | 构建器模块/版本/是否清场 | `clear_scene: true` |
| `contract` | 构建时契约校验结果（`ok` + `checks[]`） | 452 项 |
| `artifact` | 场景文件 SHA-256 + 字节数 | `bf7e4df6...` / 2797905 |
| `extra` | 扩展区：`extra.v1` 放契约版本、产品版本、控制器 ID、配置摘要副本 | 见下 |
| `note` / `actor` | 人写的备注 / 谁做的 | `"v1 consolidation M3"` / `"cli"` |

两个读 manifest 时的注意点：

1. **新建工件 vs 迁移工件的字段位置不同**。`store.build_manifest()`（`artifacts/store.py:284`）会在**顶层**写 `product_version` 和 `scene_contract_version`；而当前这个迁移工件把它们放在 `extra.v1.product_version` / `extra.v1.contract_version`。所以查版本号要**两个地方都看**。
2. **`config.digest` 是"代码-场景"的契约锁**。它由 `config_base + config_motion + config_dual + config` 的可序列化常量算出（排除 `MODEL_BASE`、`DEFAULT_LOG_FILE`）。改了任何一个容差，digest 就变，旧工件的 `validate` 立刻失败。**这是"不能偷偷调参"的技术手段。**

### 2.3 生命周期日志 `lifecycle.jsonl`

每次 `load`/`start`/`stop`/`finish` 追加一行（JSON Lines），包含时间、actor、状态、run_id。用来回答"这个工件最后一次被谁在什么时候动过"。

### 2.4 保护规则（五条，背下来）

1. 每次 `save`/`migrate` 创建**新目录** `v<NNN>_<stamp>`，永不覆盖；
2. `protected: true` → 拒绝覆盖，文件系统只读；
3. `migrate` 失败**不更新 current**，也不改源工件；
4. `build` 只做契约检查，`build → save` 才落新版本；
5. 不许用 CoppeliaSim 的 **File > Save Scene** 覆盖工件里的 `scene.ttt`。

## 3. 目录数据库（catalog.db）

### 3.1 为什么要数据库

代码里的默认工艺目录（`default_process.py`）是**唯一真相**，但它不能查、不能发版、不能对比。数据库化是为了：

- 让工艺目录**可版本化发布**（staging → published）；
- 让"代码目录"和"数据库目录"能**逐字段对比**（`catalog diff`）；
- 给前端/仪表盘/订单提供查询入口。

### 3.2 六个 Alembic revision（schema 演进）

| revision | 内容 |
|---|---|
| `0001_catalog_core` | 静态目录：物料类型、设备、能力、场景绑定、互斥资源、区域、配方/工序/路线/入口及关系表 |
| `0002_knowledge_graph` | 知识图谱：来源、抽取运行、实体/关系、来源追溯 |
| `0003_run_records` | 运行快照与事件：`production_run`、工序实例、物料实例、谱系、资源事件、运行事件 |
| `0004_order_catalog_metadata` | 订单编排需要的端口/allowlist/场景字段 |
| `0005_orders` | 版本化订单与订单运行关联 |
| `0006_order_planner_metadata` | planner 输入/explain/候选数 |

### 3.3 发布流程（四步，都幂等）

```powershell
flexible-factory catalog init                    # 建表/升级到 head
flexible-factory catalog import                  # 代码目录 → staging release（单事务）
flexible-factory catalog publish --release-id X  # 校验 + 原子发布
flexible-factory catalog diff                    # 代码 vs 数据库，必须 ok:true
flexible-factory catalog verify                  # 结构/外键/往返校验
```

- **release 子表复合主键都以 `release_id` 开头** → 外键天然不会跨版本串数据；
- `staging → published` 是**一个事务**，发布失败不留半成品；
- `run --catalog-source db` 会在**连仿真器之前**做同样的等价检查，不一致直接拒绝启动；
- 数据库不可用/没有 published release 时**不会回退到代码目录**，报 `CATALOG_*` 错误。

### 3.4 默认路径与保护

`var/catalog/catalog.db`（38.9 MB）。`var/` 被 `.gitignore` 忽略；**绝不允许写进 `docs/scene_artifacts/`**。连接级 `PRAGMA foreign_keys=ON` 失败即拒绝运行——宁可跑不起来，也不要静默放弃外键。

## 4. 运行记录（run records）

### 4.1 铁律：只在两个边界写库

```text
RunRecorder.start   → 写一行 production_run(RUNNING)
RunRecorder.finish  → 一个事务内批量写：工序实例 / 物料实例 / 谱系 / 资源事件 / 运行事件 + 终态
sim.step() 热路径   → 绝不写 SQL
```

为什么：仿真循环一步 0.05 s，任何同步 IO 都会让节拍失真。所以设计成"内存里攒，结束时一次性落库"。

失败处理：**写库失败只标记 `run_record.ok = false`**，不回滚仿真、不自动重放。失败/中止的运行**也写终态**（`ABORTED`/`FAILED`），否则查不到"失败现场"。

### 4.2 七张表

| 表 | 内容 |
|---|---|
| `production_run` | 一次运行的汇总（run_id、scenario、artifact、目录版本、终态、时间） |
| `operation_instance` | 每个工序实例（instance_id、node/template、设备、状态、阶段） |
| `operation_instance_input/output` | 输入输出物料绑定 |
| `material_instance` | 每个物料（UID、类型、状态、区域） |
| `material_genealogy` | 谱系（成品 ← 哪些父件） |
| `resource_event` | 资源申请/释放/等待 |
| `run_event` | 运行事件（调度决策、失败、冻结） |

### 4.3 Q1–Q4 查询（不需要仿真器）

```powershell
flexible-factory report runs                              # Q1 运行汇总与验收
flexible-factory report run     --run-id <id>             # Q1 单次
flexible-factory report genealogy --uid <final_uid>       # Q2 成品谱系
flexible-factory report waits   --resource arm_A          # Q3 资源等待/竞争
flexible-factory report timeline --instance-id <id>       # Q4 工序时间线与失败取证
```

不传 `--run-id` 时默认最近一次。想直接看表就用 SQLite 或仪表盘：

```powershell
uv run python .\tools\db_dashboard.py --db .\var\catalog\catalog.db --out .\dashboard.html --open
```

仪表盘是**自包含 HTML**（不依赖 CDN），展示知识图谱、运行记录 Q2–Q4、工艺目录 DAG（工序依赖、路线卡片、资源申请顺序、设备能力、区域容量）、发布状态。

## 5. 知识图谱（Neo4j → SQLite）

真实数据来自 `fmpmm.dump`（一个 **Neo4j 数据库 dump**，项目本身不解析二进制）：

```text
fmpmm.dump
   │  官方 neo4j-admin 载入（Docker Neo4j 5.13）
   ▼
Neo4j 数据库
   │  tools/neo4j_export.py 只读导出
   ▼
export.json（节点/关系 + 原始 ID + 来源定位）
   │  flexible-factory knowledge import
   ▼
SQLite staging extraction（记录来源 SHA-256、抽取器版本）
   │  knowledge verify（未映射标签/谓词、端点缺失、canonical ID 冲突 → 阻断）
   ▼
knowledge publish
```

实测结果：**222 实体 / 384 关系**，无未映射、无冲突、无悬空关系（`docs/implementation/reports/data-platform/v1-knowledge-graph-import.md`）。

关键设计：**未映射就不发布**。宁可少导入，也不要往图谱里塞一堆"未知关系"。

## 6. 订单：不可变版本

```text
订单 JSON（只有 8 个字段）
   │  domain/orders.py           严格拒绝未知字段/代码字段/句柄
   ▼
OrderSpec ── domain/order_validation.py ── 结构/端口/环/可达
   │
   ├─ domain/order_compiler.py   → OperationInstance 图 + MaterialPlan（确定性 UID）
   ├─ application/planner.py     → 从目标反推草稿（可选）
   ▼
persistence 版本表（order_version）
   │  数据库触发器禁止 UPDATE  → 只能追加新版本
   ▼
运行：绑定 {不可变版本 + 目录版本 + 具体 artifact ID}
```

几个"为什么"：

- **为什么版本不能改**：订单运行中途改了图，正在跑的实例就对不上号了。所以"改订单"= 建新版本；旧版本永远可复现。
- **为什么绑定 artifact**：同一个订单在 `v001` 和 `v002` 工件上跑，结果可能不同。绑定后"这次跑的是哪个场景"没有歧义。
- **为什么 API handler 不持句柄**：worker 独占 runner 线程和仿真连接，HTTP 只读写数据库。这样刷新页面/断网不会影响正在跑的运行。

API 面（`api/server.py`，默认 `127.0.0.1:8080`）：

```text
GET  /api/health
GET  /api/templates
GET/POST /api/orders
GET  /api/orders/{order_id}
GET/POST /api/orders/{order_id}/versions
GET  /api/orders/{order_id}/versions/{version}
POST /api/orders/preview
POST /api/orders/{order_id}/versions/{version}/preview
POST /api/orders/{order_id}/versions/{version}/start
GET  /api/orders/{order_id}/runs
GET  /api/runs/{run_id}  |  /nodes  |  /events
POST /api/runs/{run_id}/stop
POST /api/planner/plan  |  /api/planner/drafts
```

⚠️ 首期**没有认证/TLS**，只绑 loopback。别拿它当对外服务。

## 7. 五条数据设计原则

| 原则 | 体现 | 好处 |
|---|---|---|
| **不可变** | 工件新目录、订单新版本、触发器禁 UPDATE | 任何历史结果都可复现 |
| **原子** | current 原子更新、发布单事务、配对原子消费、资源全有或全无 | 不会出现"半成品状态" |
| **边界写库** | 只在 start/finish 写运行记录 | 仿真节拍不失真 |
| **摘要校验** | manifest 存 config digest + scene sha256 + model 尺寸 | 改了东西一定会被发现 |
| **不做静默回退** | 数据库不可用不回退代码目录；校验失败拒绝启动；写库失败不回滚仿真 | 失败是响亮的，不是隐蔽的 |

最后一条最值得学：**很多工程事故不是"没做对"，而是"做错了但没说"**。这个项目在每一处都选择了"大声失败"。
