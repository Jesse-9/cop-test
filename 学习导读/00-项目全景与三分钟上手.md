# 00 · 项目全景与三分钟上手

## 1. 一句话定位

> **`flexible-factory` 1.0.0** 是一个"柔性工业车间"的数字化仿真：用 Python 作为**唯一时钟主控**，通过 **ZeroMQ Remote API** 远程驱动 **CoppeliaSim 4.10**，在虚拟车间里完成"两种原料 → 三条工艺路线 → E 岛配对 → 一个成品"的全流程，并把过程写成可核验的 JSON 证据。

它不是一个"机械臂抓手"的小 demo，而是一个**小型生产系统**：有工艺目录（配方）、工序图、资源互斥、调度策略、故障隔离、版本化订单、数据库和前端工作台。

一句话拆开看四个关键词：

| 关键词 | 含义 | 在项目里对应 |
|---|---|---|
| 柔性（flexible） | 同一套设备能跑不同批次/不同产品路线，不是硬编死的流水线 | `domain/process_model.py` 的配方目录 + `application/batch.py` 的批次配比 |
| 车间（factory） | 多工位、多设备、有物流和缓冲区 | 五岛 A–E + 四条传送带 + 一台 AGV |
| 仿真（simulation） | 物理在 CoppeliaSim 里算，决策在 Python 里做 | `simulation/`（几何/物理/运动）+ `application/coordinator.py`（决策） |
| v1 产品 | 收敛成单一入口、单一运行模式、受保护工件 | `flexible-factory` 命令 + `full_flow` 模式 + `docs/scene_artifacts/v1/` |

## 2. 它到底在仿真什么

俯视布局（`simulation/config.py` 的 `UNIT_DEFS`，X 为主输送方向，Y 为横向，单位 m）：

```text
                      y=+1.35   ┌───────── C→E 传送带 ────────┐
                                │                             │
   S1 仓库                      │                             ▼
   (RAW_A) ──带──► A ─固定交接──► C ───────────────────────► E ──► FINAL
                   ▲                                          ▲
   (RAW_B) ──带──► B ──AGV B→A──┘                            │
                                                             │
   S2 仓库 (RAW_D) ──带──► D ────AGV D→E───────────────────────┘
                      y=-1.35

   A/B dock 在 x=0.40，D/E dock 在 x=2.90，
   AGV 走"西直道 → 南横道 → 东直道"的 U 形外围路网（只在节点处停车转向）
```

- **A 岛**是混线的关键：壳体（housing）既能从 S1 直接来（`housing_direct`），也能从 S1 经 B + AGV 绕一圈再来（`housing_alt`）。**同一个成品，两条供料路线**，这就是"柔性"的最小演示。
- **E 岛**是配对点：壳体（`SEMI_CE`）+ 支架（`PART_DE`）原子配对成 `FINAL`。缺一件就**不会**生成成品——这是"逻辑合流"，不是真的物理装配。
- **四台臂之外还有第五台**：C 和 E 之间靠传送带，D 和 E 之间靠 AGV，所以五台 UR5 各管一段。

## 3. 技术栈

| 层 | 选型 | 版本/位置 |
|---|---|---|
| 仿真器 | CoppeliaSim Edu | 4.10+，ZMQ Remote API 监听 `localhost:23000` |
| 内置模型 | UR5 / suction pad / pioneer p3dx / generic conveyor | `C:\Program Files\CoppeliaRobotics\CoppeliaSimEdu\models` |
| 语言 | Python | `>=3.11`（`pyproject.toml`） |
| 包管理 | uv | `uv sync`；`uv.lock` 锁版本 |
| 运行时依赖 | `coppeliasim-zmqremoteapi-client>=2.0.4`、`sqlalchemy>=2.0.36`、`alembic>=1.14` | 只有三个，很克制 |
| 前端 | React + TypeScript + Vite + React Flow | `frontend/`，独立 workspace，只吃 `/api` |
| 数据库 | SQLite + SQLAlchemy 2.x ORM + Alembic | 默认 `var/catalog/catalog.db` |

设计上一个很重要的取舍：**除了"连仿真"和"存数据"，其余全是纯 Python 数据结构**。所以 62 个测试文件、近 1 万行测试，大部分**不需要 CoppeliaSim** 就能跑（`pytest -q`）。这让"改业务逻辑"的成本非常低。

## 4. 三分钟上手

### 前置（缺一不可）

1. 装好 CoppeliaSim 4.10 或更新版本；
2. 打开 CoppeliaSim，菜单 **Add-ons → ZMQ remote API server**，确认监听 `localhost:23000`；
3. 在项目根目录执行 `uv sync`（第一次会建 `.venv`，约 120 MB）。

### 三条命令

```powershell
flexible-factory load                                          # 加载 v1 工件，不清场、不重建
flexible-factory validate                                      # 可选诊断：只读校验
flexible-factory run --scenario full_flow --time 700           # 跑正式流程（约 700 仿真秒上限）
```

跑完你会看到：

- 控制台/日志：`[TASK][v1] scenario=full_flow fault=none batch=...`、`[DONE][v1] 报告写入 ...`；
- 报告：`docs/implementation/runs/v1_run_full_flow_<时间戳>.json`（含验收项、物料证据、AGV 证据）；
- 数据库里多一条运行记录（`--run-records off` 可关）。

### 不想开仿真器也能先玩

```powershell
python -m pytest -q                          # 纯逻辑回归，不需要 CoppeliaSim
flexible-factory catalog init                # 建目录库
flexible-factory catalog import               # 把代码里的默认工艺导入为 staging
flexible-factory catalog publish --release-id <上一步返回的 id>
flexible-factory catalog diff                 # 代码目录 vs 数据库目录，必须 ok:true
flexible-factory report runs                  # 看历史运行记录（Q1）
```

## 5. 必须先懂的 9 个概念

这 9 个词在代码和文档里高频出现，先记住对应关系，后面读代码会顺很多。

| # | 概念 | 一句话解释 | 代码位置 |
|---|---|---|---|
| 1 | **场景工件（artifact）** | 一个版本的场景快照目录：`scene.ttt` + `manifest.json` + `validation.json` + `lifecycle.jsonl` | `artifacts/store.py` |
| 2 | **manifest** | 工件的"身份证 + 体检报告"：schema 版本、配置摘要、场景 SHA-256、来源追溯、alias 清单 | `artifacts/store.py:284 build_manifest` |
| 3 | **契约（contract）** | 场景必须满足的对象/别名/物理条件，校验不过就拒绝启动 | `simulation/contract.py` |
| 4 | **生命周期（lifecycle）** | `DISCONNECTED → CONNECTED_STOPPED → SCENE_LOADED → SCENE_VALIDATED → SIMULATION_RUNNING`，非法跳转会被拒 | `application/lifecycle.py:73` |
| 5 | **工艺目录（catalog）** | 配方 + 工序模板 + 路线 + 入口 + 设备 + 区域，一份**静态、可校验**的描述 | `domain/process_model.py`、`domain/default_process.py` |
| 6 | **工序实例（OperationInstance）** | 一次运行里"某一件物料的某一道工序"的唯一状态记录 | `domain/operation_runtime.py:97` |
| 7 | **协调器（coordinator）** | 唯一调度者：决定谁动、谁等、谁提交；也是唯一的 `sim.step()` 调用点 | `application/coordinator.py:96` |
| 8 | **执行适配器（executor）** | 把"控制器/航线"包一层，只做 `start/pre_tick/post_tick/poll`，**不 step** | `simulation/execution/base.py` |
| 9 | **运行记录（run record）** | 只在运行开始/结束两个边界批量写库的工序/物料/资源/事件快照 | `persistence/runs.py:40` |

还有两个容易混的：

- **scenario vs batch**：`scenario` 是"跑哪个验收场景"（`full_flow` 是唯一用户模式，其余是回归）；`batch` 是"这次投多少原料"（`RAW_A/RAW_B/RAW_D` 各几件）。批次**只改数量**，不改路线、不改设备、不改工件。
- **recipe 模式 vs order 模式**：前者按固定配方跑有限批次（`run` 命令）；后者按用户画的 DAG 跑（`order start` / `api serve` + 前端）。两者共用同一套 `OperationGraph/OperationRuntime` 生命周期，但入口和校验不同。

## 6. 项目现在能做什么、不能做什么

这一节很重要。项目文档反复强调"**不得把计划描述成已具备能力**"，因为这里混着三种东西：已实机验收的、只有纯逻辑测试的、还没做的。

### 已经做过、有实机证据的

| 能力 | 证据 |
|---|---|
| v1 五岛 `L5_UFLOW` 场景 + `full_flow` 全流程（FINAL 1 件，父 UID `[1,3]`） | `docs/implementation/evidence/v1_*_acceptance_20261103_*.json` |
| 有限批次配比 3 个 profile 实机通过（FINAL 1/2/1） | `docs/implementation/reports/production-flow/v1-mixed-production-flexibility-demo.md` |
| 阶段 4 能力调度：13 任务、12 工序实例、11 条可解释调度决策、资源清零 | `docs/implementation/evidence/production-flow/v1_stage4_full_flow_20261104_210605.json` |
| 订单 DAG 阶段 6：手工/planner 订单各 1 个 FINAL，`NODE_PRECHECK_REJECTED` 局部拒绝，真实安全锁存 → `ABORTED` | `docs/implementation/evidence/order-orchestration/v1_order_dag_phase6_acceptance_20261108.json` |
| 数据平台：目录库导入/发布/影子对比、运行记录 Q1–Q4、Neo4j 知识图谱 222 实体/384 关系 | `docs/implementation/reports/data-platform/*.md` |

### 只有纯逻辑测试、**没有**实机准入的

- 任意 DAG / 任意设备替换（planner 只把"已登记路线"当 macro，不自由拼边）；
- 真实 Arm/AGV 运动错误、ZMQ 连接断开、stepping 故障的分类隔离——**一律按 GLOBAL 处理**；
- 多订单并行、订单间的资源竞争；
- WP3（设备替代）、WP4（同一 UID 运行中动态选路）。

### 明确不在范围内

- 统一故障**自动恢复**（安全锁存不会自动清除，这是刻意的）；
- MCP 服务器（已从 v1 移除）；
- MES/ERP 集成、跨场景调度；
- API 的认证/TLS（首期只绑 `127.0.0.1`，只能当本机工具用）。

判断一个说法可不可信的方法：看它有没有 `docs/implementation/evidence/` 里的 JSON，或者报告里有没有写明"实机执行时间 + 结论"。**没有证据的能力描述，按"计划"理解。**

## 9. 读这个项目的正确姿势

1. **先看业务再看代码**：把 [01 篇](01-业务与工艺主线.md) 的流程图自己画一遍，再打开 `domain/default_process.py`，你会发现代码几乎是这张图的直译。
2. **先看测试再看实现**：`tests/test_v1_*.py` 的命名就是行为清单（`test_v1_base_conveyor_transport`、`test_v1_coordinator_scheduler`……）。想改某个行为，先找对应测试。
3. **文档和代码冲突时信代码**，但**代码和证据冲突时信证据**（报告里的实测数字是当时的运行结果，代码可能已经迭代）。
4. **不要一次读 coordinator.py**。2625 行的正确读法是：先读它的模块 docstring（第 1–25 行，把单步顺序写清楚了），再只看 `step()` 和 `_dispatch_ready()`，其余按需跳转。
5. **任何"我改一下试试"都要在 `--artifact` 副本或新工件上做**。`docs/scene_artifacts/v1/` 下的工件是 `protected: true` + 只读，改了摘要校验就过不了。
