# 动力学仿真设计

## 定位

CoppeliaSim 是**混合仿真器**：kinematics（运动学）与 dynamics（动力学）并用，按场景取舍。物理引擎仍依赖大量近似，相对不精确且较慢——**能用运动学就用运动学**（如机械臂本体），仅在必须时才用动力学（如夹爪抓取、移动机器人与地面接触、自由落体）。

只有 **shape / joint / force sensor** 三类对象会被动力学仿真，且取决于场景结构与对象属性是否"动态启用"（dynamically enabled）。仿真中动态启用对象在场景层级旁会显示专用图标；应启用但无法启用的对象会显示警告图标。

## 5 个物理引擎

可在 `dynamicsEngineDialog` 随时切换，引擎间存在[小差异](physicsEngineDifferences.htm)：

| 引擎 | 类型 | 特点 |
|------|------|------|
| **MuJoCo** | 开源 | 高保真，支持软体/绳/弹性/肌腱/关节依赖约束等；可经 [simMujoco XML 注入](simMujoco.htm) 覆盖引擎特有参数。4.x 推荐 |
| **Bullet** | 开源 | 游戏物理引擎，3D 碰撞 + 刚体 + 软体，通用 |
| **ODE** (Open Dynamics Engine) | 开源 | 刚体 + 碰撞，游戏物理引擎 |
| **Vortex Studio** | 商业 | 高保真、参数对应真实物理单位，工业/研究级；需向 CM Labs 注册免费 license |
| **Newton Dynamics** | 跨平台 | 确定性求解器（非传统 LCP/迭代），兼具稳定性与速度 |

> 各引擎对同一场景的接触/约束处理有差异（如闭环、static shape 摩擦、weld 约束刚性），见 `physicsEngineDifferences.htm`。MuJoCo 中 static shape 以 mocap body + weld 约束表示，闭环以 weld 约束表示（可能偏软，可调 `mujoco.overlapConstrSolref/Solimp/Torquescale`）。

## Shape 的动态四象限

shape 按 **static/non-static** × **respondable/non-respondable** 分四类（`shapeDynamicsProperties`）：

| 属性 | 含义 |
|------|------|
| **static** | 位置相对父对象固定，不受重力/约束影响（如地面、机架） |
| **non-static** | 受重力及动态约束（动态启用关节/力传感器/overlap）直接影响 |
| **respondable** | 碰撞时产生碰撞反应（互相弹开）；两 respondable shape 的碰撞 mask 不重叠则不反应 |
| **non-respondable** | 不参与碰撞反应 |

> 碰撞 mask 在 `shapeDynamicsProperties` 设置。MuJoCo 中 static shape（mocap body）不传摩擦力，故总以 mocap + weld 连一个 non-static free body（除非其 `kinematic` property 为 false）。

## 动态约束与闭环

两 shape 间的动态约束通过**动态启用**的 joint / force sensor，或 **dummy-dummy dynamic overlap constraint** 建立：

- **动态启用的 joint/force sensor**：连接两 shape 形成简单约束（关节允许相对运动、力传感器为刚性链接）；
- **overlap constraint**：用于闭环（并联机构）或跨树的刚性绑定——两个 dummy 经 `setLinkDummy` 设为 dynamic overlap 类型，可构成刚性约束或闭环；
- **rigid compound**：多个 non-static shape 想作为单一刚体，用 `[Edit > Shape grouping/merging > group]` 合并，并修正惯性矩阵；若需差异化动态属性（不同摩擦），则用 force sensor 刚性连接。

## Primitive shape 优先

为碰撞响应准备的 shape 应是 **primitive shape**（cuboid/cylinder/sphere）或 primitive compound——它们在物理引擎中**快且稳定**。非 primitive（simple/convex mesh）碰撞慢且不稳，应隐藏于不可见层（如 layer 9），仅作视觉，碰撞用隐藏的 primitive 替身。详见 [[02-仿真建模/02-02-形状与几何体]]。

## 关节的动态模式与控制

关节处于 **dynamic 模式**时由动力学模块处理（须与连接对象构成有效配置才动态启用）。控制模式见 `jointDynamicsProperties`：

| 控制模式 | API | 说明 |
|---------|-----|------|
| motion (position) | `sim.setJointTargetPosition` | 动力模式下目标位置（经 PID/电机模型逼近） |
| velocity | `sim.setJointTargetVelocity` | 速度控制 |
| force/torque | `sim.setJointTargetForce` | 力/力矩控制 |
| free | — | 自由（无主动控制） |

> kinematic 模式关节不受动力学模块处理，用 `sim.setJointPosition` 瞬时设位或 `setJointTargetPosition` 走 profile。详见 [[02-仿真建模/02-03-关节与关节模式]]。

## 力传感器

force sensor 须**动态启用**才工作（作为两 shape 间刚性链接，可测 6 维力/力矩，可因阈值断裂）。详见 [[02-仿真建模/02-06-力传感器]]。

## 质量与惯性

- `sim.computeMassAndInertia(shape, density)`：按 shape 几何与给定密度**自动计算质量与惯性矩阵**，是设置动态属性的首选；
- `sim.getShapeMass` / `sim.setShapeMass` / `sim.getShapeInertia` / `sim.setShapeInertia`：手动读写；
- 合并 shape 后须修正惯性矩阵。

## 步长关系

| 步长 | 默认 | 说明 |
|------|------|------|
| 仿真步长 (simulation time step) | 50 ms | `sim.getSimulationTimeStep`，控制/感知逻辑每步一次 |
| 动力学步长 (dynamics time step) | 5 ms | 物理引擎细分步，`dynamicsDialog` 可调 |

动力学步长是仿真步长的 1/10（默认），物理引擎在每个仿真步内做多次细分。**力控制 / 低层关节控制**若需精细，应使仿真步长等于动力学步长，并在 stepping 模式下每步触发（外部应用为 clock master）。详见 [[01-API参考/01-02-Remote-API-ZMQ]]。

## 可运行示例

动态启用关节目标位置 + 自动质量惯性计算的 stepping 循环：

```python
# Python (ZMQ Remote API 客户端，CoppeliaSim 4.10)
from coppeliasim_zmqremoteapi_client import RemoteAPIClient

client = RemoteAPIClient()
sim = client.require('sim')

# 假设场景中已有 /robot 且其关节为 dynamic 模式
joint = sim.getObject('/robot/joint1')
link_shape = sim.getObject('/robot/link1')

# 按几何与密度自动算质量/惯性（仅非 static shape 需要）
sim.computeMassAndInertia(link_shape, 7800.0)  # 钢密度 kg/m^3

sim.setStepping(True)
sim.startSimulation()
try:
    t = 0.0
    while t < 5.0:
        # 动态模式下设目标位置（弧度），物理引擎逼近
        sim.setJointTargetPosition(joint, 1.57)
        sim.step()
        t = sim.getSimulationTime()
        print(f't={t:.2f}  pos={sim.getJointPosition(joint):.3f}')
finally:
    sim.stopSimulation()
```

> 若 `getJointPosition` 不随时间变化，检查：关节是否为 dynamic 模式、连接的 shape 是否 non-static 且 respondable、是否构成有效动态配置（场景层级无警告图标）。
