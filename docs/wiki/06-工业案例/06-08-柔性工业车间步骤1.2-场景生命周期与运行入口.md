# 柔性工业车间步骤 1.2：场景生命周期与运行入口

> 本文是 [[wiki/06-工业案例/06-05-柔性工业车间分阶段执行步骤]] 中步骤 1.2
> 的独立执行计划。目标是为阶段二提供可重复使用、可校验的场景工件和统一运行
> 入口；它不实现或验收碰撞、接触、避障、故障恢复等仿真物理行为。

## 1. 目标与边界

阶段一当前主要通过运行入口构建场景并进入仿真。阶段二需要反复调整碰撞集合、
TCP 接触参数、路径与故障处理。如果每次启动都隐式清场并重新构建，实验难以从
完全相同的场景继续，也容易把“启动”误做成破坏现有状态的操作。因此，本步骤先
建立明确的场景工件生命周期：

```text
显式构建 → 契约校验 → 另存场景工件 → 加载已有工件
                                      ↓
                              只读校验 → 显式启动/停止
```

本步骤负责：

- 拆分构建、保存、加载、只读校验、启动和停止的动作与接口；
- 定义阶段一/阶段二场景工件、manifest、版本和变更保护；
- 让 CLI 与 MCP（如使用）遵循相同生命周期语义；
- 验证退出、重启 CoppeliaSim 后可从保存工件恢复，而不是必须重新构建。

本步骤不负责：碰撞集合与允许碰撞对的物理正确性、TCP 是否进入物体、避障路径
是否无碰撞、故障恢复策略、conveyor 停机安全性、内置模型脚本的最终剥离策略。
这些仍由阶段二相应条目设计、实现和验收。步骤 1.2 只提供扩展 manifest 和场景
契约的机制。

## 2. 开始前的盘点与保护

1. 记录当前分支、工作区状态、阶段一报告版本、当前场景配置和已有场景文件；保留
   未提交改动，不把既有用户文件当作可清理的生成物。
2. 盘点 `src/stage1/scene.py`、`src/stage1/run.py`、兼容入口以及 MCP server 中
   现有的 build/start/stop 行为，尤其检查启动是否会调用 `build_scene(clear=True)`、
   是否会停止或重置另一个正在运行的任务。
3. 盘点阶段一当前场景输入：布局配置、内置模型路径、传感器/设备 alias、TCP 与
   几何测量、物理参数、脚本处理记录、运行模式以及场景契约断言。
4. 选定专用场景工件目录。阶段一通过基线、步骤 1.1 结果和阶段二实验场景分开
   保存；阶段一通过工件设为只读父版本，阶段二必须从该工件复制/派生，不得从头
   重建后冒充同一基线，也不得覆盖基线文件。阶段二默认保持几何、布局、坐标、模型
   和物理参数不变；只有验证证据证明必要时，才在阶段二副本中做最小、可追溯的变更。
   覆盖已有工件必须通过显式、可审计操作，默认采用新版本路径。
5. 为所有破坏性或状态转换动作确定前置条件：仿真运行时不能加载/重建场景；存在
   未停止运行时不能启动第二个仿真控制任务；失败时保留原场景和错误诊断。

盘点结果形成简短的现状与差距清单，作为本步骤验收记录的一部分。

**盘点结果 (2026-10-20)**：

- 分支 `codex/step1.2-lifecycle`；工作区保留了用户未提交的
  `PHASE1_REPORT.md`、06-05、06-07 修改和 06-08 新文件，未改动
  `scenes/*.ttt`、日志或用户配置。
- `src/stage1/run.py` 每次运行都 `build_scene(clear=True)`，隐式清场重建；
  `src/reference/factory_mcp_server.py` 的 stage1 `start` 也在内部调用
  `build_scene(clear=True)`。两者都违反“start 不隐式构建”。
- 没有场景保存/加载/版本化工件、manifest、只读校验、跨进程运行锁或
  生命周期状态记录；MCP 的 `build_scene` 只返回构建报告，不产生工件。
- 已有场景文件 `scenes/3arm_simulation_test.ttt`、`scenes/stage2_scene.ttt`
  是既有文件，不被本步骤读取或覆盖。
- 阶段一当前场景输入集中在 `stage1/config.py` + `stage1/layout.py`（L1_S1），
  构建契约由 `Stage1Scene.verify()` 的 43 项检查给出（v002 保存时为 42 项；新增 UR5 关节模式检查在加载校验时执行）。

## 3. 定义生命周期契约

### 3.1 动作语义

为每个动作定义唯一、明确的输入、输出、失败状态和允许的仿真状态：

| 动作 | 语义 | 禁止的隐式副作用 |
|---|---|---|
| `build_scene` | 按指定配置从空白/专用构建场景创建对象并执行构建期变更 | 不得由普通 start 调用；不得清理非本构建器管理的对象 |
| `save_scene` | 将已通过构建校验的停止态场景保存到新工件版本 | 默认不得覆盖已验收工件 |
| `load_scene` | 在仿真停止态加载指定 `.ttt` 工件 | 不得自动改写、重建或升级模型 |
| `validate_scene` | 读取场景并验证 manifest、对象身份和契约 | 必须只读，不得修复、重命名或补建缺失对象 |
| `start_simulation` | 仅启动当前已加载且校验通过的场景 | 不得清场、重建、加载默认场景或静默切换后端 |
| `stop_simulation` | 停止当前仿真并等待停止态确认 | 不得删除场景、重置到另一工件或丢弃诊断信息 |

接口名称可因 CLI/MCP 框架不同而异，但动作语义、参数和错误分类必须一致。构建
和仿真运行是两个阶段；需要构建新场景时必须显式请求构建。

### 3.2 状态机与非法转换

至少区分 `DISCONNECTED`、`CONNECTED_STOPPED`、`SCENE_LOADED`、
`SCENE_VALIDATED`、`SIMULATION_RUNNING` 和 `ERROR` 等可观测状态。实际实现可以
采用等价枚举，但必须能区分：已连接不等于场景已加载；场景已加载不等于校验通过；
仿真运行中不能重建或替换场景。

至少拒绝以下转换并返回明确原因：

- 仿真运行中调用 build/load；
- 未加载场景或契约校验失败时调用 start；
- 同一服务对已运行中的仿真重复启动第二个控制循环；
- 使用不存在或路径越界的场景工件；
- 未经显式授权尝试覆盖只读/已验收基线。

启动失败不得伪报成功，也不得留下后台任务持续控制旧场景。

## 4. 场景工件与 manifest

### 4.1 工件布局

阶段一基线、阶段二开发场景和临时诊断场景使用不同命名空间或目录。工件至少由
以下部分构成：

```text
<scene-artifact>/
  scene.ttt
  manifest.json
  validation.json
  lifecycle.jsonl
```

实际目录/文件名可服从仓库现有规范，但必须能从验证报告定位到精确的 `.ttt`、配置
版本和代码提交。大体积运行日志或逐步物理轨迹可单独存档，并由 manifest/报告引用。

### 4.2 manifest 最低字段

manifest 应描述可重建和校验场景的稳定信息：

- schema 版本、工件 ID、创建时间、来源阶段、代码提交和配置摘要/哈希；
- CoppeliaSim 版本、物理引擎、仿真步长和运行模式；
- 内置模型路径及版本/校验摘要，外部资源引用；
- 布局 ID、世界坐标约定、设备/传感器/物料对象的稳定 alias 与类型；
- 几何测量、TCP 偏移和当前阶段已冻结的物理参数；
- 构建期脚本保留/剥离记录、构建器版本及场景契约断言结果；
- manifest 自身版本及与场景文件的关联摘要。

对象句柄是当前仿真会话中的运行时值，重新加载场景后可能变化；不能把旧句柄当成
跨会话身份。manifest 应保存稳定 alias/类型等身份信息，加载后重新解析句柄，并验证
唯一性与对象归属。阶段二增加碰撞集合、白名单、接触参数和路径配置时，按向后兼容
规则扩展 manifest schema，不破坏阶段一工件的读取能力。

### 4.3 保存与版本保护

1. 仅在仿真停止态保存；保存前重新执行构建契约校验。
2. 每次正式保存创建新的版本化工件；若仓库采用固定“当前”指针，该指针只能在新
   工件成功写入并再次加载验证后原子更新。
3. 使用临时路径写入并确认文件完整后再发布工件，避免中断留下看似有效的半成品。
4. 基线工件设为只读/受保护输入；实验脚本只在专用输出目录创建副本或新版本。
   阶段二副本需保存父工件 ID/摘要及差异清单；若无经论证的物理改动，其场景内容
   应与阶段一父工件保持一致，仅增加阶段二所需的 manifest/契约数据。
5. 保存失败、空间不足、资源缺失等情况必须明确报错；不能只在日志中告警后继续启动。

## 5. CLI 与 MCP 运行入口

1. CLI 暴露独立的构建、保存、加载、校验、启动和停止模式；参数命名与 MCP 工具
   对应动作保持一致。兼容入口可保留，但不能改变默认安全语义。
2. 如通过 MCP 控制阶段一/阶段二，提供等价的显式操作或等价的分步工作流。MCP 的
   start 请求必须使用当前已加载并已校验的工件；如果没有合格场景，应返回“需要先
   构建/加载并校验”的明确状态，不能在 start 内暗中调用 build。
3. 对耗时仿真返回可追踪的运行 ID 和状态；重复 start 对同一运行应幂等或明确拒绝，
   不得创建两个同时调用 `sim.step()` 的后台循环。
4. 控制面输出场景 ID、manifest 版本、加载/校验状态、仿真状态和错误摘要。详细日志
   留在结构化生命周期记录中，不能把成功响应等同于任务物理验收通过。
5. CLI 与 MCP 可共用内部服务层，但不能由旧版五岛 backend 静默接管阶段一/阶段二
   工件；backend/场景类型必须显式或由工件 manifest 唯一确定。

若当前版本尚未提供 MCP 入口，本步骤应完成接入或记录 MCP 未纳入目标运行方式的
明确决策。不能保留“工具存在但 start 实际重建另一套旧场景”的歧义。

## 6. 加载、校验和启动流程

1. 调用方选择显式工件 ID/路径；解析后的绝对路径必须位于配置允许的场景工件目录。
2. 确认连接正常且仿真停止；如已有仿真运行，先要求显式停止并确认，不能自动中断
   未知任务。
3. 加载已保存 `.ttt`，确认仿真仍处于停止态；读取 manifest 并检查 schema 版本。
4. 只读枚举场景对象，重新映射 alias 到本会话句柄；检查必需对象唯一、对象类型和
   层级契约符合 manifest。
5. 比较 CoppeliaSim/模型/配置/场景版本及场景摘要。任何影响行为的差异都返回差异
   报告并拒绝 start；不得自动修补后继续运行。
6. 校验通过后记录 `SCENE_VALIDATED`，再由独立 start 动作启动仿真；停止时记录停止
   原因与最终状态，并等待 Remote API 返回可确认的停止态。
7. 同一工件重复加载/校验/启动/停止，结果应可复现；控制器启动后重新建立所有
   runtime handles，不依赖前一轮仿真缓存。

校验器必须只读。若检测到缺失对象、重复 alias、版本漂移或物理引擎不符，应停止在
启动前，并提供建议的显式“重建新版本”操作；不能在当前调用里无提示重建。

## 7. 测试与通过门槛

### 7.1 测试矩阵

| 场景 | 操作 | 通过条件 |
|---|---|---|
| 首次构建 | 显式 build → validate → save | 生成完整新工件与 manifest；对象契约通过 |
| 分步运行 | load → validate → start → stop | start 不触发 build/clear；运行和停止状态可确认 |
| 进程重启恢复 | 关闭并重启 CoppeliaSim，再 load 已保存工件 | 不重建对象即可恢复、校验并运行 |
| 重复运行 | 同一工件连续加载/启动/停止多轮 | 不重复对象、不使用陈旧句柄、无残留后台循环 |
| 版本不匹配 | 修改配置/模型摘要或 manifest 版本 | 校验失败并列出差异；不启动、不覆盖原工件 |
| 场景不完整 | 移除必需 alias 或制造重复 alias | 校验失败；不自动补建或重命名 |
| 非法状态 | 运行中 build/load、未校验 start、重复 start | 动作被拒绝且返回可识别错误 |
| 工件保护 | 构建/保存阶段二实验场景 | 阶段一基线哈希和文件未变化 |
| MCP/CLI 一致性 | 对两种入口执行同一生命周期序列（如两者均纳入） | 状态转换、副作用和错误分类一致 |

至少保留可离线运行的 lifecycle 状态/接口单元测试，以及需要 CoppeliaSim 的最小
集成验证；报告中分开标注两类测试，不以 mock 测试代替真实保存/重载验证。

### 7.2 通过条件

- 构建、保存、加载、只读校验、启动和停止是可单独调用的动作；start 不隐式清场
  或重建；
- 场景保存后重启 CoppeliaSim 可加载、校验并重复运行；
- manifest 可解析稳定对象身份，加载后重新获取句柄；版本/契约不匹配时在 start 前
  失败并给出可诊断差异；
- 阶段一基线与阶段二实验场景隔离，普通运行命令不会覆盖基线；
- CLI 与 MCP（若列为交付入口）具有一致生命周期语义，不存在并发重复 stepping；
- 输出工件、结构化生命周期记录和复现步骤，可供阶段二直接引用。

任何一项未通过时，步骤状态保持“进行中/未通过”，阶段二可以进行不依赖该入口的
离线设计工作，但不得把场景复用和运行解耦列为已完成能力。

## 8. 交付物

- 生命周期接口/状态转换说明和现状差距记录；
- 版本化阶段一场景工件及 manifest、只读校验报告；
- 阶段一基线与阶段二实验工件隔离规则；
- CLI/MCP 操作说明及非法状态、失败行为；
- 自动化测试结果和至少一次 CoppeliaSim 进程重启后的真实保存/重载证据；
- 提供给阶段二的场景 ID、manifest schema 版本、加载/校验入口，以及扩展物理契约
  时的兼容约束。

### 11.2 状态机

```text
DISCONNECTED ──connect──→ CONNECTED_STOPPED
CONNECTED_STOPPED ──build──→ SCENE_VALIDATED
CONNECTED_STOPPED ──load──→ SCENE_LOADED ──validate──→ SCENE_VALIDATED
SCENE_VALIDATED ──save──→ SCENE_VALIDATED (新工件, 重载校验通过)
SCENE_VALIDATED ──start──→ SIMULATION_RUNNING ──stop──→ SCENE_VALIDATED
任意状态 ──disconnect──→ DISCONNECTED; 校验失败 ──fail──→ ERROR
ERROR ──load/build──→ 显式恢复
```

运行中 `build`/`load`/`save`/`validate`/重复 `start` 均被状态机拒绝；
跨进程由 `docs/scene_artifacts/.runtime/run.lock`（PID + run_id）拒绝第二路
控制循环。`prepare_start` 在只读校验**之前**获取运行锁，避免校验窗口内被
另一进程 load/build。

### 11.3 manifest schema 1.0

`manifest.json` 已实现 §4.2 的全部稳定字段：schema/工件 ID/时间/阶段/
代码提交与脏标记、配置摘要与 165 项配置快照、CoppeliaSim 版本与物理引擎
（`bullet`）、4 个内置模型的 sha256、布局、26 个对象身份（alias/类型/父
alias/世界坐标，**不含运行时句柄**）、几何/TCP、物理参数、脚本保留/剥离
记录、构建器版本与 43 项构建契约结果（v002 保存时记录 42 项）、场景文件 sha256/大小。

阶段二扩展规则：保持 `schema_version = "1.0"` 的读取能力；新增碰撞集合、
允许碰撞对、接触参数、路径配置时写入 `extra` 或升 `schema_version` 的新
字段，不得删除/重命名已有字段。阶段二工件必须 `--parent` 指向 v002
（未指定会被拒绝）；`parent_artifact.differences` 记录 config/layout/
models/objects/geometry/tool/physics/scripts 的章节级差异，objects 另列
新增/移除 alias。

### 11.6 已知边界

- 本步骤不验证碰撞集合、TCP 穿透、避障、conveyor 停机安全性或脚本最终
  剥离策略；这些仍属于阶段二。
- manifest 校验比较配置摘要、模型摘要、仿真器版本/引擎、对象身份/位姿和
  构建契约；它是“场景可复用性”校验，不是物理正确性证明。
- `save` 默认拒绝保存“构建后已运行”的非初始位姿场景；确需快照时使用
  `--allow-after-run`，且该工件不得作为基线。
- 受保护工件不再追加 `lifecycle.jsonl`；运行/校验事件写入
  `.runtime/lifecycle.jsonl`，以保证基线文件哈希不变。
