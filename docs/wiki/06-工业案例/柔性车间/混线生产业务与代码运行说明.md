# 混线生产业务与代码运行说明

本文概述当前 v1 混线生产仿真的业务含义、工序路线、程序运行链路和代码模块，
作为阅读工艺映射、实施报告与源码的入口。本文记录截至 2026-11-04 的实现状态；
具体设备 alias、逐工序端口和场景对象映射以
[[wiki/06-工业案例/柔性车间/当前规划/06-25-混线生产工艺流程与设备映射]]
为准，验收结论以对应阶段实施报告为准。

## 1. 当前范围

当前产品以五岛车间 `L5_UFLOW` 场景和 v1 默认配方 `mixed_line_v1` 为基础，
通过有限批次仿真验证混线工艺。它不是订单/MES 系统：当前没有订单实体、
用户运行时编辑配方或基于订单的动态路线选择。工序与设备候选来自代码内的
静态目录；运行中的工序依赖图按来料入口和该入口绑定的路线实例化。

截至本文日期，阶段 0-4 已完成并有各自的实施报告。阶段四接入了可解释、
确定性的 ready 工序派工策略，但默认工艺的物理工序仍各只有一个设备候选，
因此不代表已经完成跨设备替代。阶段五的优化与有限恢复仍是后续规划。

## 2. 业务对象与路线

| 对象                  | 业务含义                      | 运行中的作用                             |
| ------------------- | ------------------------- | ---------------------------------- |
| `RecipeSpec`        | 一组默认工艺定义                  | 声明入口、工序模板、路线和合流                    |
| `OperationTemplate` | 一类可执行或逻辑工序                | 声明端口、能力、候选设备、资源和验证器                |
| `RouteVariant`      | 一条有序工序路线                  | 按入口固定选择并实例化为工序链                    |
| `OperationInstance` | 某个物料在某次运行中的工序实例           | 持有唯一运行状态、前驱、输入/输出 UID 和调度结果        |
| `Stage4Task`        | 供队列和执行流程使用的兼容投影           | recipe-backed 任务代理工序实例，不另存一份生命周期状态 |
| 物料账本/区域             | 物料身份、类型、位置、状态与谱系          | 验证输入输出、区域容量和最终父子 UID               |
| 资源                  | 机械臂包络、AGV lane、dock 等互斥占用 | 执行前原子申请，结束后释放                      |

`full_flow` 默认投入 `RAW_A=1`、`RAW_B=1`、`RAW_D=1`。路线固定如下：

| 入口物料 | 路线 | 中间物料与终点 |
|---|---|---|
| `RAW_A` | `line_s1a` → A → C → E | `SEMI_AC` → `SEMI_CE` → `buffer_e_c` |
| `RAW_B` | `line_s1b` → B → AGV B→A → A → C → E | `SEMI_AB` → `SEMI_AC` → `SEMI_CE` → `buffer_e_c` |
| `RAW_D` | `line_s2d` → D → AGV D→E → E | `PART_DE` → `buffer_e_d` |

当两个 E 缓冲区分别有 `SEMI_CE` 和 `PART_DE` 时，逻辑工序 `kit_join` 配对
并生成 `FINAL` 到 `output_e`，保留两个父物料 UID。示例验收中 UID 1 与 UID 3
生成 UID 4；UID 2 留在 `buffer_e_c` 作为未配对壳体。这是批次输入和合流规则的
结果，不是执行异常。

工序路线上定义的是物料加工与交接依赖；仿真任务时间线还可能含 AGV 空载调机、
区域等待和资源等待。`reposition` 是运行时物流任务，不是配方工序：当待执行的
AGV 装载、卸载或运输请求要求车辆位于另一个 dock，协调器会按需创建空载路线任务，
把 AGV 调到目标 dock，再继续处理业务任务。它经 `Stage4Task`/`TaskQueue` 管理，
不属于配方 DAG，没有 `OperationInstance`，也不产生 recipe 工序派工决策。其他仍
使用旧任务状态接口的入口是 `make_task()` 的兼容构造路径（主要供兼容测试）；
普通区域/资源等待是状态和等待记录，不是额外的旧生产流程。E 合流由协调器逻辑
处理，不进入机械臂任务队列，也不表示发生了真实机械装配。

## 3. 一次运行的代码链路

```text
CLI / 生命周期入口
  → 构建并校验场景、目录、资源与执行组件
  → run_scenario_v1()
  → Stage4Coordinator.start()
  → step 循环
      → 检查入口批次与区域容量，生成物料
      → 按入口固定路线实例化 OperationInstance DAG
      → 取得 ready 工序并调用纯调度策略
      → 认领实例、登记所选设备、投影 Stage4Task
      → 原子申请资源并启动机械臂/AGV Executor
      → 协调器推进控制器、航线和唯一 sim.step()
      → 验证执行与物料结果，提交物料账本
      → 提交 OperationInstance，解锁后继
      → 检查并提交 E 逻辑合流
  → finished / acceptance / summary / evidence
```

运行过程的关键边界如下：

1. **入口生成与建图。**协调器依据场景批次和来源区域容量生成物料，登记 UID、
   类型、来源和当前位置；随后由入口 ID 找到固定 `RouteVariant`，逐工序创建
   实例并建立前驱关系。未选路线不会被同时实例化。
2. **ready 判定与调度。**只有所有实际前驱均已成功提交的工序才可派工。协调器
   为 ready 工序建立只读快照，纯策略按 recipe 候选范围、静态能力、场景绑定、
   物料/区域条件和当前资源/设备状态给出候选解释、选择结果或等待原因。
3. **派工与执行。**选定设备写入工序实例后，任务队列任务只是该实例的投影。
   协调器根据工序类型交给机械臂或 AGV executor；执行器不拥有业务账本，也不调用
   仿真步进。所需资源通过资源表整体申请，申请失败时记录等待，不留下部分资源锁。
4. **仿真步进。**`run_scenario_v1()` 驱动协调器的 `step()`；协调器轮询来源、
   任务和执行器，推进 AGV 航线及控制器，再调用 `sim.step()` 并收集结果。仿真
   每步只有协调器负责推进。
5. **成功提交。**执行器成功只表示动作阶段完成，不直接解锁后继。协调器先检查
   UID、类型、位置、物料状态和物理属性，更新物料流转/区域账本；账本成功后才由
   `OperationRuntime.commit_success()` 登记输出并完成工序实例。
6. **失败与合流。**执行、验证或账本提交失败时，工序不会以成功状态解锁后继。
   AGV 到站后也需通过航线验证和物料提交。合流只从已经提交的工序输出中选取输入，
   两个父实例及物料提交完成后才记 `FINAL`。
7. **结束与证据。**结束条件同时检查活动任务和工序图完成情况。摘要包含任务、
   工序实例、调度决策、物料、路线和验收字段；超时/冻结运行不应描述成完整通过。

## 4. 模块职责速查

| 模块 | 主要职责 |
|---|---|
| `src/flexible_factory/cli.py`、`application/lifecycle.py` | CLI 命令及应用生命周期、场景加载与收敛 |
| `application/run.py` | 验收场景运行循环、超时/停止处理、结果证据组装 |
| `application/coordinator.py` | 单步编排、来源生成、ready 派工、设备执行、物料提交、合流和验收 |
| `domain/process_model.py`、`domain/default_process.py` | 工艺数据结构、静态目录、默认 recipe 与校验 |
| `domain/operation_runtime.py` | 运行上下文、实例 DAG、ready 判定、设备选择和唯一生命周期迁移入口 |
| `domain/scheduling.py` | 消费纯数据快照并产出候选过滤/派工决策；不控制仿真、不申请资源 |
| `domain/tasks.py` | 任务队列与 `Stage4Task` 投影；配方任务状态由 `OperationRuntime` 管理 |
| `domain/materials.py`、`domain/resources.py` | 物料/区域/谱系账本及资源互斥申请、释放 |
| `simulation/device_binding.py` | 目录设备到场景与运行时对象的静态绑定核对 |
| `simulation/execution/arm.py`、`agv.py` | 包装既有机械臂控制器与 AGV 航线执行生命周期 |
| `simulation/scene.py`、`runtime.py`、`unit_controller*.py`、`agv*.py` | 场景对象、运行时资源、机械臂和 AGV 实际仿真动作 |

### 4.1 术语规范与文档统一步骤

当前实现同时包含配方工序 DAG 和历史任务队列接口。为避免把静态定义、运行实例、
执行请求及仿真对象混为一谈，后续文档按以下术语表达：

| 规范术语 | 对应对象 | 使用边界 |
|---|---|---|
| 配方（recipe） | `RecipeSpec` | 可复用的静态工艺定义，包含入口、工序定义、路线变体和逻辑合流定义 |
| 工序定义（operation template） | `OperationTemplate` | 静态描述输入/输出、能力、候选设备、资源及验证器；不带单次运行状态 |
| 路线变体（route variant） | `RouteVariant` | 同一入口/路线组可选的一条有序工序定义序列；当前入口固定选择，不代表动态选路 |
| 工序实例（operation instance） | `OperationInstance` | 某次运行中针对具体物料 UID 的工序；工序图中的唯一生命周期状态记录 |
| 工步定义引用（work-step template reference） | `WorkStepTemplateRef` | 工序内部引用的已登记执行步骤，不是独立派工工序 |
| 执行任务（execution task） | 当前物理工序对应的 `Stage4Task` 视图 | 现阶段供旧队列/执行接口使用；配方工序的真实状态仍归工序实例所有 |
| 空载调机任务（empty reposition task） | `kind="reposition"` 的 `Stage4Task` | 协调器按需生成的 AGV 物流任务，不属于配方工序 DAG |
| 物料区域（material zone） | `MaterialPort.zone`、`ZoneSpec` | 物料账本中的逻辑位置和容量约束；通过绑定关联到物理承载，不等同于场景小岛对象 |
| 互斥资源（exclusive resource） | `ResourceTable` 中的资源 ID | 运行期间原子申请/释放的占用权；即使与区域同名，也与物料位置账本分属不同模型 |
| 场景对象别名（scene object alias） | `DeviceBinding.aliases` 等 | 用于将稳定工程 ID 解析到 CoppeliaSim 场景对象；不是工序、区域或资源本身 |

文档统一按以下步骤维护：

1. **先按对象层次命名。**描述静态复用定义时使用“工序定义/路线变体”；描述某个 UID
   在某次运行中的状态时使用“工序实例”；描述进入执行接口的对象时使用“执行任务”。
   避免单独用“工序”指代定义和实例，除非上下文已明确。
2. **明确兼容层和运行时物流。**提到 `Stage4Task` 时说明它是执行任务接口/视图；提到
   `reposition` 时说明它是协调器生成的空载物流任务。不要把它列入 recipe 路线、工序 DAG
   或工序实例数量。逻辑合流则称“逻辑工序/合流工序”，并说明它不创建物理执行任务。
3. **分别描述位置、占用和几何对象。**“物料区域”只描述账本位置与容量；“互斥资源”描述
   执行期占用；“CoppeliaSim 场景对象/别名”描述物理场景实体。说明它们如何绑定时引用
   `device_binding.py` 或具体场景映射，不假设三者一一对应。
4. **按文档职责更新，不复制另一套定义。**本说明维护业务边界和术语入口；`06-25` 维护
   逐工序、端口和场景 alias 映射；阶段实施报告记录对应版本的实际实现与验收。改动后
   检查这三处是否互相引用、是否把规划能力误写成已实现能力。
5. **代码标识保留原样并配规范释义。**代码、JSON、事件和证据中的既有字段/ID（如
   `Stage4Task`、`kind`、`task_id`、`operation_instance_id`）在引用时不翻译或静默改名；
   新文档首次出现时给出规范术语和角色。代码 API 或序列化字段若要改名，另立代码迁移
   任务，列出调用方、历史证据读取和版本兼容要求，不把文档术语整理扩大为隐式重构。

## 5. 调度与设备能力边界

阶段四的调度器基于稳定输入快照生成可序列化决策，并通过事件和 summary 留下
候选拒绝原因、选择设备、等待原因、资源结果和执行 ID。资源表仍是资源占用的
权威来源；调度策略只观察资源 owner，实际资源通过协调器原子申请。

默认工艺中的物理工序各只有一个候选设备。能力目录说明设备可提供的静态能力，
并不自动证明另一台设备可以安全接替某工序。动态几何、IK、碰撞和路径仍由执行
阶段检查；未经对应目标组合实测的设备候选不应当作可用替代。设备健康、工具载荷、
姿态包络等当前没有权威数据源，调度证据将其标为未建模维度，不静默视为通过。

WP5（扩大等价候选）未实施；WP6（AGV 停靠/接触余量复核）未执行。阶段四验收
通过不代表跨设备替换已验收，也不代表运动误差余量充足。默认工艺未增加重试、
故障后重派、路线自动变更、抢占或全局最优求解。

## 6. 当前验收状态

截至 2026-11-04，阶段四报告记录：WP0–WP4 已完成；纯逻辑测试为
**450 passed / 3 skipped**；`full_flow` 实机验收通过。验收包含 12 个工序实例、
13 个任务、11 条物理调度决策、1 件 `FINAL`（父 UID `[1, 3]`），资源结束时清零。
阶段四证据中的 11 条物理决策均选定 recipe 候选并取得资源。

AGV 停靠误差仍接近 `0.02 m` 判据上限；报告明确未据此宣称运动余量充足。
上述数字和验收结论来自特定日期、工件和仿真环境下的阶段报告，不保证其他场景、
设备组合或故障情形都已验证。
