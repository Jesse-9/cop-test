# 柔性车间混线生产：工序配方与设备调度演进规划

> 目标是在保留阶段四已验证的运动、物料和安全逻辑基础上，逐步把固定工艺映射演进为可配置工序配方与基于设备能力的派工。先让现有场景以工序计划稳定跑通，再加入产品变体、候选设备、分支/合流和调度优化。

## 1. 结论与术语

工序调度和设备建模不是互斥方案，也不是同一层对象。混线生产以**工序实例**作为生产调度单位，以**设备资源/执行端**作为能力提供者，以**工步**作为设备或工序执行时的细化步骤。推荐组合“配方驱动工序 DAG”与“每类设备有执行端/适配器”的方案；设备可有本地命令队列，但生产订单的依赖关系仍由工序图管理。

本文为本项目采用以下术语，避免把领域中偶有重叠的词混用：

| 层次 | 名称 | 定义 | 当前例子 |
|---|---|---|---|
| 产品/订单 | 工艺配方 Recipe | 某产品可复用的工序模板及其依赖、输入输出和路由选择规则 | “组件 X：加工壳体 → 检验 → 与支架配对” |
| 生产调度 | 工序 Operation | 对物料执行的可派工、可验收、可占用资源的工作模块 | “把 UID 12 从 AGV 取下并放到 A→C 交接台” |
| 执行细化 | 工步 Work Step | 工序内部有序或有条件的执行步骤；通常由设备执行端推进，不各自成为生产订单 | “确认 dock → 机械臂接近 → 吸取 → 抬升 → 放置 → 验证” |
| 执行器 | 动作 Action | 可复用的设备级控制原语或持续控制过程，有输入、运行状态、结果 | arm `pick_place`、AGV `follow_route`、conveyor `run_until_zone` |
| 车间资源 | Resource | 需要独占、限量或互斥的设备/区域/物料位置 | `arm_A`、`agv_lane_west`、`buffer_e_c`、`dock_A` |
| 物理设备 | Device / Executor | 暴露能力、运行状态和动作接口的机械臂、AGV、传送带等 | UR5 A、Pioneer AGV、`line_ce` |

设备的“独立可编排”应体现为调度器可以发现它的能力、状态和资源约束，并向它下发工步/动作；不意味着把设备本体当作一条生产任务。维护、回零、换工具等设备生命周期工作可以另建设备管理任务，但不应与产品工序混为一个 `TaskKind`。

## 2. 当前工作区基线

阶段四已有任务状态、优先级/去重、全量资源申请、物料 UID/类型/区域检查、机械臂状态机、AGV 路线状态机和逐仿真步协调。`Stage4Task` 已记录 UID、kind、来源/目标、设备、状态、资源、时间和证据；`TaskQueue` 管生命周期，`ResourceTable` 管互斥。

柔性能力的主要缺口在固定映射，而不在缺少所有基础设施：

- `src/stage4/config.py` 的 `TASK_KINDS`、`TASK_FLOW` 和 `TASK_PRIORITY` 固定任务目录与示例流程。
- `src/stage4/coordinator.py` 的 `UNIT_TASKS`、`TASK_RESOURCES`、`TASK_TYPES`、`TASK_SOURCE/SINK`、`TASK_SOURCE_ZONE/TASK_DEST_ZONE`、`FOLLOWUP` 将工序绑定到固定工位、物料类型、资源和后继。
- `_poll_unit` 只按固定工位取任务；`_start_unit_task` 直接构造 `Stage4UnitController`；`_check_join` 特判 E 岛合流并生成 FINAL。
- 机械臂取放的细步在 `Stage4UnitController` 继承的状态机内；AGV 的载货路由/空载调位有独立任务；传送带启停和输送在任务控制器及每仿真步逻辑中，尚无通用的按 UID 输送操作模板。
- 设备能力未成为通用派工输入。现有任务通常在类型上已隐含指定工位，因此同一工序的替代工位和路线切换需要代码修改。

保留现有重要不变量：一个物料在交接期间保持单一 UID/谱系；工序输出只有验证通过才提交物料区域/类型变更；资源按固定顺序一次申请；物理执行和碰撞检查继续使用已验收控制器；场景对象通过 alias/契约解析，不把句柄写入持久配方。

## 3. 用现有场景表达一个简单生产故事

建议将当前五岛场景解释为“**两种壳体供料路线 + 一种支架供料 + E 岛成套配对**”的混线装配单元。这只是对已有几何和物料流的业务命名，不声称场景已经模拟真实切削、检测或物理装配。

| 当前物流 | 简单业务意义 | 当前可观测结果 |
|---|---|---|
| S1→A→A→handoff_ac→C→line_ce→E 缓冲 C | 壳体 X 的直达加工路线 | 经过 A/C 两工位后成为 `SEMI_CE` |
| S1→B→AGV B→A→handoff_ac→C→line_ce→E 缓冲 C | 壳体 X 的替代/绕行供料路线 | B 预加工后经 AGV 到 A，再汇入 C 工序 |
| S2→D→AGV D→E→E 缓冲 D | 支架 Y 的独立供料路线 | D 加工后成为 `PART_DE` 并送到 E |
| E 缓冲 C + E 缓冲 D→E_Output | 成套匹配/逻辑装配 | 配对成功后生成一个有父 UID 记录的 `FINAL` |

这样可以自然展示混线主题：相同壳体可以走不同前段路线，共享 A/C/E 能力与缓冲；支架路线独立运行，在 E 等待壳体配套。当前 `RAW_A` 与 `RAW_B` 路线都进入 A→C 链，是不同来料路径的示例；它们是否代表同一可销售产品，应由未来配方和物料主数据明确。E 的 `FINAL` 目前是逻辑配对产物，不是机械臂真实装配动作。

第一阶段不需要重建场景。可以先将现有物料名改为 `HOUSING_DIRECT`、`HOUSING_PREPROCESSED`、`BRACKET` 等业务描述，保留既有 enum 和证据兼容；待流程数据化稳定后，再决定是否改物料主数据。

## 4. 目标模型

```text
订单/产品型号
  └─ 配方版本 (Recipe DAG)
       ├─ 工序模板 (输入/输出、能力要求、前置条件、验收规则)
       └─ 路由/分支/合流/返工规则
             ↓ 实例化
       工序实例 (UID/订单、依赖、优先级、候选设备、状态、证据)
             ↓ 可行性与资源检查
       调度器 (依赖 + 物料位置 + 能力 + 资源 + 策略)
             ↓ 指派
       设备执行端 (机械臂 / AGV / 传送带 / 工艺处理器)
             └─ 工步状态机与动作适配器
                   ↓ 完成/失败/阻塞结果
       质量/物料谱系提交、工序解锁、指标事件
```

### 配方和实例

配方模板只放稳定的工艺意图，不放运行时句柄和单次 UID。订单释放时将模板实例化为工序实例并为依赖边分配唯一 ID。工序字段建议逐步增加：

```text
operation_instance_id, order_id, recipe_id, recipe_version
operation_template_id, product_id, material_inputs[], material_outputs[]
predecessor_instance_ids[], capability_requirements{}
candidate_device_ids[], resource_request[], source_zone, target_zone
priority, due_time, state, current_step, evidence, failure_policy
```

工序完成后由验证器检查结果，再原子提交输入消费/输出生成和区域变化；后继工序只在依赖满足后进入 ready 集合。配方校验应拒绝循环依赖、悬空能力、无效物料类型、输入输出不匹配、缺少完成条件、引用未知区域等配置错误。

### 工步、动作和设备端

工序模板可以引用版本化的工步模板。例如机械臂的 `pick_place` 工步模板由现有状态机执行，不应为每个 `APPROACHING`、`ATTACHING` 状态新增全局生产任务；这些状态可作为工步内部阶段及观测证据。

设备端使用稳定接口而不暴露 CoppeliaSim handle：

```python
class DeviceExecutor(Protocol):
    def capabilities(self) -> set[str]: ...
    def status(self) -> DeviceStatus: ...
    def can_accept(self, step: WorkStep) -> Feasibility: ...
    def start(self, step: WorkStep) -> ExecutionId: ...
    def poll(self, execution_id: ExecutionId) -> StepResult: ...
```

当前实现范围只需要 `start/poll` 包装现有控制器，不引入复杂设备插件发现或 cancel/recovery 协议。单个实体设备应有设备 ID（如 `arm_A`），设备类型/能力可被多个实例共享（如 `robotic_pick_place`）。共享区域、buffer、dock 和 lane 仍由资源表或容量资源模型管理，不伪装为可执行器。

### 调度边界

调度器每次仿真步只挑选 ready 工序：输入已到位、前置工序已完成、候选设备能力匹配、设备空闲且完整资源集可获得。它可以根据订单优先级、等待时间或交期排序；短期先保留可解释的 priority/FIFO，不先引入全局优化求解器。设备本地队列可用于已预留资源后的命令排队，但不能绕过中央物料所有权和依赖检查。

## 5. 配方示例

以下是结构示意，字段需经后续 schema 定稿；不要求首阶段直接引入 YAML。

```yaml
recipe_id: housing_bracket_v1
product_id: assembled_module
route_variants:
  housing_route:
    direct: [housing_direct_A]
    alternate: [housing_alt_B, transport_BA, housing_alt_A]
operations:
  - id: housing_direct_A
    inputs: [housing_raw]
    outputs: [housing_at_handoff]
    capability: robotic_pick_place
    candidate_devices: [arm_A]
    source: line_s1a
    destination: handoff_ac
    steps: [wait_for_material, pick_place, verify_handoff]

  - id: housing_alt_B
    inputs: [housing_raw]
    outputs: [housing_on_agv]
    capability: robotic_pick_place
    candidate_devices: [arm_B]
    source: line_s1b
    destination: agv
    steps: [wait_for_material, pick_place, verify_load]

  - id: transport_BA
    inputs: [housing_on_agv]
    outputs: [housing_at_A]
    capability: agv_transport
    candidate_devices: [agv_1]
    depends_on: [housing_alt_B]
    route: dock_B_to_dock_A

  - id: housing_alt_A
    inputs: [housing_at_A]
    outputs: [housing_at_handoff]
    capability: robotic_pick_place
    candidate_devices: [arm_A]
    depends_on: [transport_BA]
    source: agv
    destination: handoff_ac
    steps: [verify_input, pick_place, verify_handoff]

  - id: housing_finish
    inputs: [housing_at_handoff]
    outputs: [housing_finished]
    depends_on: [housing_route.terminal]
    capability: robotic_pick_place
    candidate_devices: [arm_C]
    route: handoff_ac_to_line_ce
    steps: [verify_input, pick_place, verify_output]

  - id: bracket_process
    inputs: [bracket_raw]
    outputs: [bracket_finished]
    capability: robotic_pick_place
    candidate_devices: [arm_D]
    route: line_s2d_to_agv

  - id: kit_join
    inputs: [housing_finished, bracket_finished]
    outputs: [assembled_module]
    depends_on: [housing_finish, bracket_process]
    capability: logical_kit_join
    candidate_devices: [logic_E]
    steps: [match_parentage, validate_pair, commit_output]
```

要点：上面的 `route_variants` 是示意字段，配方实例化时只选择 direct 或 alternate 一条路线，`housing_finish` 依赖所选路线的终点，不是同时等待两个路线分支。配方定义可选工艺路线；工序实例决定某个订单选择哪条路线；设备候选由能力、几何可达性和场景配置共同过滤；E 合流由多输入依赖表达，而不是靠 coordinator 中只针对 E 的隐藏特例。未来若需要真实装配，再把 `logical_kit_join` 换成机械臂/夹具动作配方，不改变上游工序图概念。

## 6. 分阶段实施

各阶段以当前 `L5_UFLOW` 工件和 `full_flow` 为基线。当前实施范围的仿真验收只运行 `full_flow`；暂不运行 `no_pair`、`agv_priority`、故障注入或异常恢复场景。必要的安全联锁仍保留在生产执行代码中，但本轮不扩展或验收其异常分支。完成 `full_flow` 等价/目标行为不代表阶段四所有故障场景重新验收，也不改变项目已有的全局安全约束。

### 阶段 0：冻结现状契约与业务基线

**目的：**确保后续架构整理能证明等价运行。

- 整理 `PHASE4_REPORT` 中当前工件、`full_flow` 流程、运行命令和已知安全边界；把本文的壳体/支架解释标为示例语义。
- 只将 `full_flow` 作为本计划的端到端仿真基线；其它验收场景和异常注入结果可引用历史报告，不在本轮重跑或作为阶段门槛。
- 记录当前生产任务、AGV 运输、传送带运行/停止、E 配对的事件追踪样例。

**验收：**无生产逻辑变化；基线能在当前工件上重复运行；每件物料的 UID、工序、区域和最终状态可从事件追溯。

### 阶段 1：从协调器抽出静态工序目录

**目的：**把硬编码表集中为代码内的数据定义，尚不开放用户配方。

- 新增 `src/stage4/process_model.py`（名称可随实现调整），定义 `OperationTemplate`、`InputSpec`、`OutputSpec`、依赖、能力要求、候选设备、资源、工步模板引用和验收规则。
- 将 `TASK_KINDS`、`TASK_RESOURCES`、类型/源/汇/区域映射及 `FOLLOWUP` 合并成 `DEFAULT_RECIPE` / `ProcessPlan`；不要再让同一任务语义散落在 config 和 coordinator 两处。
- 保持 `Stage4Task` 对外证据字段及 legacy task kind 序列化兼容，在内部增加 `operation_instance_id` 等字段的渐进适配。
- `Stage4Coordinator` 改为读 `ProcessPlan`，但仍调用原 `Stage4UnitController` 和 AGV route controller。
- 把 E 的 join 前置/输入/输出契约变成模板数据，但先继续使用原验证与提交函数。

**验收：**默认配方与现有任务图一致；旧测试/证据 schema 未意外破坏；`full_flow` 结果与阶段 0 基线一致。纯模型验证可覆盖非法依赖/未知引用等配置错误，但不注入运行异常。此阶段的核心不是减少行数，而是建立单一、可校验的工艺定义来源。

### 阶段 2：引入设备目录和执行适配器

**目的：**组合“工序中央调度 + 设备执行端”，复用现有硬件仿真控制逻辑。

- 新增物理设备目录：`arm_A`…`arm_E`、`agv_1` 和 `line_s1a`…`line_ce`；实体句柄仅在 scene/runtime 绑定阶段解析。逻辑 join 是软件工序，不注册成物理设备。
- 注册当前确有执行实现的能力：机械臂取放与 AGV 路线。传送带先作为由现有 conveyor controller 驱动的共享设备/资源，传感器作为条件读取接口；只有将来实现并验证按 UID 输送 executor 后，才注册 `conveyor_transport` 能力。
- 新增 `ArmExecutor` 包装 `Stage4UnitController`，`AgvExecutor` 包装 `AGVRouteController4`。E join 由 operation/process handler 执行，不创建虚拟实体设备。按实际需要添加适配器，不为所有对象强行实现相同接口。
- executor 返回逐 tick 执行结果和证据；正常路径使用 `RUNNING / SUCCEEDED`，资源/前置条件等待由工序 runtime 表达。保留底层失败结果以免误报成功，但本轮不扩展重试、恢复或异常分类。物料提交由 coordinator/runtime 的单一事务边界负责。
- 单一 stepping loop 持有 CoppeliaSim 写操作和 `sim.step()`；执行器只由协调器在 tick 中调用/轮询。初期不要每设备另开线程并发写远程 API。

**验收：**默认配方经 adapter 执行后 `full_flow` 通过；仿真仍由唯一 stepping loop 推进；executor 与 coordinator/runtime 不双重提交物料状态。暂不增加故障注入、BLOCKED 恢复和 cancel 场景。

### 阶段 3：将配方实例化为工序 DAG

**目的：**先实现可配置的一条现有工艺，再实现多型号。

- 新增订单/配方加载和 `RecipeValidator`；先支持顺序依赖和 AND 合流，不支持任意脚本或用户 Python 回调。
- 新增 `OperationInstance` 最小生命周期：`WAITING_INPUT`、`READY`、`RESERVED`、`RUNNING`、`SUCCEEDED`、`FAILED`。资源忙时保留为 READY/WAITING_RESOURCE 的正常等待；BLOCKED/CANCELLED/恢复状态留待后续需求。执行器状态是局部执行记录，operation runtime 是唯一工序状态所有者。
- 由订单释放创建物料 UID 和工序实例；工序成功后验证器提交物料输出，再解锁后继。阶段四旧流程由默认 recipe 完全表达，包括 E 的双输入 join。
- 建一个简洁的 JSON 或 Python 数据配方先跑通；选择单一格式，字段校验清晰。不要同时实现 YAML、JSON、UI 编辑器和数据库。
- 将遗留 `FOLLOWUP` 转换为 recipe dependency 后删除运行时后继硬编码。

**验收：**默认 recipe 自动生成现有完整流程；可定位任一 UID 当前工序/区域；`full_flow` 成功完成且配对父 UID 正确。recipe validator 的纯数据负例覆盖循环、未知引用等配置错误；不做运行异常/故障注入测试。

### 阶段 4：混线产品变体与能力匹配

**目的：**用现有 `full_flow` 展示不同物料路线并行/交错、共享资源协调和工序汇合，再逐步让派工读取设备能力。当前只实现现有工件能证明的能力，不宣称已支持任意机械臂替代。

- 增加至少两个产品配方：例如 `housing_direct` 走 A→C，`housing_alt` 走 B→AGV→A→C；两者与 `bracket` 在 E 做成套配对。
- 调度器从 `READY` 工序中筛选设备 `capabilities` 匹配且 `can_accept` 为真者。对机械臂，能力匹配先由静态工位能力和现有 IK/碰撞检查给出；planner 仍是最终运动可行性检查。
- 按策略选择 recipe 明确允许且静态能力匹配的候选设备；首版用固定优先级/FIFO 和稳定排序。完整记录正常派工的候选、选择和资源快照；预计队列等待、路线时间、换型时间、交期和 aging 留作后续优化。
- 共享传送带、AGV、交接区、buffer 与臂间 zone 继续使用资源约束；确认不冲突时才允许并行，不因支持混线而自动放宽已有互锁。

**验收：**唯一端到端仿真场景仍为 `full_flow`；现有 A/B/D 输入路线按 recipe 正常交错、完成 E 配对，派工记录可复现。设备替代、不可达候选和故障重派不作为本阶段验收条件。

### 阶段 5：后续调度优化与异常恢复（暂缓）

**目的：**此阶段是未来候选工作，不在当前授权范围或本轮测试计划内。只有 `full_flow` 配方与设备调度稳定并有明确业务需求后，才重新立项。

- 加入设备可用/故障、资源容量、缓冲区 WIP、换型/setup 代价、订单 due time 和可配置优先级。
- 先做局部重派：尚未执行的工序可换候选设备/路线；执行中的物理动作不抢占。工序失败后可走明确的返工/人工处理分支，而不是把 FAILED 改成 DONE 或静默自动重试。
- 实现有限的阻塞超时、撤销预留、恢复核验和任务恢复策略；每个策略都明确物料所有权、资源归还和仿真现场条件。
- 只有在简单派工数据证明规则策略不足时，再评估 CP-SAT/混合整数调度器；外部求解结果必须经过本地前置条件、能力、资源、route feasibility 验证。

**验收：**当前无阶段 5 验收门槛；未来立项时另行定义。当前阶段 0–4 不运行异常注入场景，只运行 `full_flow`。

## 7. CoppeliaSim 与执行接口约束

- 当前 Python 是 clock master。继续沿用协调器单步顺序：生成/派工 → 执行器 `pre_tick`/`poll` → AGV 控制 → 恰好一次 `sim.step()` → `post_tick`/结果验证/提交。配方解析和排程不能自己额外推进仿真。
- 项目使用 CoppeliaSim ZeroMQ Remote API / Python client。`sim.setStepping(True)` 与显式 `sim.step()` 是同步执行基础；仿真时间用 `sim.getSimulationTime()`。工序超时、输送时长、等待时间均使用仿真时间；墙钟只做 runner watchdog。
- 继续调用当前 `simIK`、关节目标、对象 pose、碰撞/距离工具和真实 scene contract。工艺配方只引用稳定的 `device_id`、`zone_id`、`target_id`；运行时由 alias/contract 把它们解析成 handle。
- 机械臂工步必须复用 `Stage4UnitController` 中的 IK、碰撞、路径、吸盘、载荷和安全锁存检查。不要把配方动作变成 `sim.setObjectPose` 直接传送机械臂或零件的捷径。
- AGV 工步复用轮速路线控制器与 route graph；配方给出起点/目标/载荷意图，不直接给 Pioneer 轮子写速度。
- 传送带区分**设备命令**（run/stop、方向/速度）和**UID 输送工序**（从源区域送到目标区域并完成传感器/位置验证）。如果多个工序共用一条带，输送工序应申请 line resource；若整线配置为连续模式，则把它建成设备运行模式，不重复发每件物料 run 命令。
- 每个工步是 tick-driven 的可轮询状态机；单次 `start()` 只下发动作，不在 Python 内阻塞等待仿真完成。长耗时工作逐 tick poll，传感器/物料条件逐步确认。不要每个设备各自使用一个 `sim.step()`。
- 一次远程 API tick 中可能包含多个读取/命令。写入顺序和控制器 pre/post 语义要保留，避免创建多个同时修改同一 joint/object 的并发客户端；优化批量远程调用须先有 profile 证据。

## 8. 建议的代码落点

先沿 `src/stage4/` 扩展，避免改动 stage1–3 的已复用控制器契约。

| 新增/调整模块 | 职责 |
|---|---|
| `process_model.py` | Recipe、OperationTemplate、WorkStepTemplate、依赖/输入输出类型 |
| `recipe_loader.py` | 默认 recipe 装载、schema 校验、版本摘要；阶段 1 可先只支持 Python 数据对象 |
| `operation_runtime.py` | 工序实例化、ready 集合、依赖推进、生命周期和证据 |
| `devices.py` | DeviceSpec、Capability、设备状态、资源映射和场景绑定 |
| `executors/arm.py` | 适配 Stage4UnitController |
| `executors/agv.py` | 适配 AGVRouteController4 和 reposition |
| `executors/line_control.py`（仅当现有接口不足时） | 薄封装传送带 run/stop 和状态读取，不把连续输送伪装为独立 UID 任务 |
| `process_handlers.py`（仅当确有多个逻辑工序时） | E logical join 等不需物理设备的工序处理 |
| `scheduler.py` | ready 工序筛选、能力/资源可行性、选择策略及决定证据 |
| `coordinator.py` | 保持单一仿真时钟、生命周期边界和工序结果提交；逐步删去固定 kind 映射 |

这些是职责候选，不要求一开始创建所有模块。先在 `process_model.py`、coordinator 和现有控制器周围完成最小迁移；仅在职责/依赖已清晰且有第二个具体用例时拆分共享接口或 handler。不得为了“插件化”预建空包。

### 实施设计约束

- **依赖方向单向**：recipe/schema 是不依赖 CoppeliaSim 的纯数据；operation runtime 管实例和依赖；scheduler 读取 ready 快照并给出选择；coordinator 持有 `sim.step()`、控制顺序和提交边界；executor 适配已有 stage4 controller。低层 executor 不反向导入 recipe loader 或调度器。
- **每类状态只有一个权威来源**：recipe 是静态意图；operation runtime 是工序状态；executor 是本次设备动作的执行状态；`ResourceTable` 是锁 owner；`MaterialRegistry/MaterialFlow` 是物料谱系和位置。设备 BUSY 从活动执行/资源 owner 派生，不再复制一份可漂移的 mutable status。
- **工序完成有单一提交点**：executor 回报设备动作成功及证据；coordinator/runtime 验证 UID、类型、位置和物理状态后提交物料输入消费/输出、工序完成和后继解锁。多输入 join 使用同一提交边界，不由 executor 与 coordinator 分别写账。
- **保留现有稳定边界**：CoppeliaSim handles 只在启动绑定/runtime 中；recipe 使用稳定 ID；阶段四控制器继续负责 IK、碰撞、吸附、运动和安全联锁；单一 stepping loop 顺序执行所有仿真写操作。
- **按当前复杂度实现**：第一轮只支持现有 `full_flow`、顺序/AND 依赖和规则派工；不引入通用插件系统、任意表达式、设备线程、事件总线或优化求解器。纯模块和数据结构只有在消除现有重复映射或满足具体调用者时才新增。

**当前验证边界：**阶段 0–4 每阶段只运行一次规定输入的 `full_flow` 端到端仿真并运行受影响的纯单元/契约测试；不运行其它 stage4 场景、异常注入或恢复验证。底层安全联锁和既有失败停止行为必须保留，但本计划不宣称异常能力已验收。

## 9. 关键设计选择及取舍

| 选择 | 优点 | 成本/风险 | 规划结论 |
|---|---|---|---|
| 工序 DAG + 中央调度 + 设备执行端 | 依赖、合流、候选设备和订单优先级可统一追踪；跨设备资源语义集中 | 初期需建立 schema、验证器和生命周期迁移 | 推荐目标架构 |
| 设备各有本地队列，中央只发命令 | 控制边界清楚，设备较多或未来分布式时有用 | 跨队列锁、物料所有权、取消/故障恢复复杂；本地可排队不代表工艺可行 | 作为 executor 内部实现的后续选项，不先做独立调度系统 |
| 扁平全局动作队列 | 易于列出每步动作和记录 | 工序依赖、物料谱系和连续所有权被拆散；容易出现孤立动作 | 不推荐作为生产任务主模型 |
| 立刻使用通用优化求解器 | 能表达多资源、替代路由和交期优化 | 建模和调参成本大；当前场景/数据规模无法证明值得 | 先规则调度，指标显示需要再选求解器 |
| 任意用户脚本配方 | 表面灵活 | 无法静态验证资源/输入输出/能力，故障与版本复现困难 | 不支持；采用声明式、有 schema 的工序与工步组合 |

## 11. 范围边界

本计划先解决“同一场景中多个产品配方、工序依赖和设备能力如何表达并运行”。首轮不要求真实制造工艺模型、视觉识别、PLC/OPC UA 接入、MES、数字孪生同步、真正机械装配、多 AGV、任意脚本配方或最优性证明。待配方驱动的默认流程和至少两种产品变体稳定后，再根据实际需求选择这些扩展。
