# 混线生产工艺流程与设备映射

> 本文回答两个问题：1）当前默认产品工艺定义中的**工序/路线/执行顺序**分别是什么意思；
> 2）文档里的 `arm_A`、`agv_1`、`logic_E`、`line_ce` 等 ID 与 CoppeliaSim
> 场景里的 alias/对象如何对应。术语的通用定义见
> [[wiki/06-工业案例/柔性车间/当前规划/06-24-混线生产术语与对象模型]]。

本文是当前 v1 静态工艺与资源定义（代码名 `ProcessCatalog`，下称“目录”）及场景绑定的参考，不表示订单级 DAG runtime、动态设备替换或所有设备都已有独立 executor。`DeviceSpec`/`CapabilitySpec` 是可复用的静态声明；运行时 scene contract/alias 绑定 CoppeliaSim 对象，资源占用由 `ResourceTable` 管理，物料位置和区域容量由物料账本 `MaterialRegistry` 管理。这里的“目录”指结构化定义集合，不是文件系统目录，也不包含这些运行时状态。

## 1. 工艺总览

当前把五岛车间解释为“两种壳体供料路线 + 一种支架供料 + E 岛成套配对”的
混线单元。业务语义是仿真抽象，不表示真实切削、检测或装配。

```text
S1 ──line_s1a──► A ──handoff_ac──► C ──line_ce──► E(b_Buffer_C) ┐
 │                ▲                                              │
 └──line_s1b──► B ─┘  (B 加工后经 AGV dock_B→dock_A 回 A)         │
                                                                  ├─► E join ─► FINAL@output_e
S2 ──line_s2d──► D ──AGV dock_D→dock_E──► E(b_Buffer_D) ─────────┘
```

- **壳体直达**：`RAW_A → A → handoff_ac → C → line_ce → E/buffer_e_c`。
- **壳体绕行**：`RAW_B → B → AGV B→A → A → handoff_ac → C → line_ce →
  E/buffer_e_c`。
- **支架**：`RAW_D → D → AGV D→E → E/buffer_e_d`。
- **E 合流**：`buffer_e_c (SEMI_CE) + buffer_e_d (PART_DE) → FINAL@output_e`。

当前 `full_flow` 批次同时投入 `RAW_A=1`、`RAW_B=1`、`RAW_D=1`，所以直达和
绕行不是二选一执行，而是分别由 UID 1（RAW_A）和 UID 2（RAW_B）两个物料实例
各走一条互斥路线；两者在 C 前汇入同一 `handoff_ac`/`housing_finish` 链。

## 2. 路线变体与执行顺序

### 2.1 路线变体

| 路线 | 组 | 工序序列 | 入口/出口 |
|---|---|---|---|
| `housing_direct` | `housing_supply` | `housing_direct_A → housing_finish → housing_to_E_buffer` | `line_s1a` / `buffer_e_c` |
| `housing_alt` | `housing_supply` | `housing_alt_B → transport_BA → housing_alt_A → housing_finish → housing_to_E_buffer` | `line_s1b` / `buffer_e_c` |
| `bracket_route` | `bracket_supply` | `bracket_process → transport_DE → bracket_to_E` | `line_s2d` / `buffer_e_d` |
| `kit_join` | 产品工艺定义中的逻辑合流 | 无路线变体；两个输入端口 | `buffer_e_c` + `buffer_e_d` / `output_e` |

`housing_direct` 与 `housing_alt` 同组互斥；不是同一订单同时走两条。`full_flow`
按入口定义固定选路，通过两个来源批次分别触发两条路线。订单 planner 可在生成
草稿时选择并生成候选订单，但订单运行图创建后不做运行时动态改线。

`full_flow` 中实际物料实例：

| UID | 来源 | 路线 | 终态 |
|---|---|---|---|
| 1 | `s1a`/`line_s1a` | `housing_direct` | `SEMI_CE` @ `buffer_e_c`，被 E 合流消费 |
| 2 | `s1b`/`line_s1b` | `housing_alt` | `SEMI_CE` @ `buffer_e_c`，未配对 |
| 3 | `s2d`/`line_s2d` | `bracket_route` | `PART_DE` @ `buffer_e_d`，被 E 合流消费 |
| 4 | E 合流 | 无独立路线 | `FINAL` @ `output_e`，父 UID `1+3` |

### 2.2 `full_flow` 的典型任务顺序

基线运行的任务/事件顺序（时间可能波动，依赖关系固定）：

```text
a_conveyor_uid1                 A 从 line_s1a 取 RAW_A → handoff_ac
b_conveyor_uid2                 B 从 line_s1b 取 RAW_B → AGV tray
d_conveyor_uid3                 D 从 line_s2d 取 RAW_D → AGV tray
reposition_uid2_toB_leg1        AGV 空载移位 A→B
c_handoff_uid1                  C 取 handoff_ac → line_ce
transport_ba_uid2               AGV 载货 B→A
e_conveyor_uid1                 E 取 line_ce → buffer_e_c
a_agv_uid2                      A 从 AGV tray 取 → handoff_ac
c_handoff_uid2                  C 取 handoff_ac → line_ce
reposition_uid3_toD_leg2        AGV 空载移位 A→D
e_conveyor_uid2 (等待)          E 取 line_ce，等待 buffer_e_c 空出
transport_de_uid3               AGV 载货 D→E
e_agv_uid3                      E 从 AGV tray 取 → buffer_e_d
E join                          buffer_e_c(uid1) + buffer_e_d(uid3) → FINAL uid4
e_conveyor_uid2 (完成)          buffer_e_c ← uid2
```

要点：

- `e_conveyor_uid2` 在 C 完成后就创建，但 `buffer_e_c` 容量为 1，必须等
  E 合流消费 uid1 后才启动；这是背压/区域占用的典型例子。
- `reposition` 是 AGV 空载移位任务，不是产品工艺定义中的工序；它只在 AGV 需要换 dock 时创建。
- E 合流不是第 14 个任务：`kit_join` 由 `_check_join` 触发并生成 FINAL，
  不进入 `TaskQueue`。
- 任务顺序受资源/优先级影响；依赖关系以 `OperationTemplate.depends_on/
  successors` 为准，而不是时间表。

## 3. 工序逐项解释

所有工序的 `candidate_devices` 当前都只有一个候选设备；`resources` 为固定
资源集，AGV 运输工序例外（按实际路线动态申请 lanes/docks）。阶段 4 的纯
策略按该候选集合筛选并记录 `DispatchDecision`；默认仍是固定设备，不开放
未验收的跨设备替代。完成验证器决定“任务 DONE”前必须核实什么。

### 3.1 `housing_direct_A`（旧 kind `a_conveyor`）

- **语义**：S1 来料直接到 A；A 从 `line_s1a` 取 `RAW_A`，转换为
  `SEMI_AC`，放到 `handoff_ac`。
- **端口**：`line_s1a:RAW_A → handoff_ac:SEMI_AC`；source/sink =
  `conveyor/station`。
- **设备/资源**：`arm_A`；`line_s1a`、`handoff_ac`、`zone_ab`、`zone_ac`、
  `arm_A`。
- **工步**：`conveyor_pickup` → `arm_pick_place`。
- **完成验证**：`unit_handoff_verified`；后继 `housing_finish`。
- **运行时任务**：`a_conveyor_uid{N}`；`Stage4UnitController`（A，line_s1a，
  dock A）。

### 3.2 `housing_alt_B`（旧 kind `b_conveyor`）

- **语义**：S1 的另一来料在 B 加工；B 从 `line_s1b` 取 `RAW_B`，转换为
  `SEMI_AB`，放到 B 的 AGV 托盘。
- **端口**：`line_s1b:RAW_B → agv:SEMI_AB`；source/sink = `conveyor/agv`。
- **设备/资源**：`arm_B`；`line_s1b`、`dock_B`、`zone_ab`、`arm_B`。
- **工步**：`conveyor_pickup` → `arm_pick_place`。
- **完成验证**：`unit_handoff_verified`；后继 `transport_BA`。
- **运行时任务**：`b_conveyor_uid{N}`；B 臂 + AGV 托盘。

### 3.3 `transport_BA`（旧 kind `transport_ba`）

- **语义**：AGV 载着 B 加工后的壳体从 `dock_B` 行驶到 `dock_A`，供 A 继续
  加工。
- **端口**：`agv:SEMI_AB → agv:SEMI_AB`；source/sink = `agv/agv`。
- **设备/资源**：`agv_1`；资源不写死，按 route spec 动态申请实际经过的
  `agv_lane_*` 和全部 dock。
- **工步**：`agv_route`。
- **完成验证**：`agv_route_verified`（停靠/航向/载荷滑移）；后继
  `housing_alt_A`。
- **运行时任务**：`transport_ba_uid{N}`；`AGVRouteController4`。

### 3.4 `housing_alt_A`（旧 kind `a_agv`）

- **语义**：A 从 AGV 托盘取 `SEMI_AB`，转换为 `SEMI_AC`，放到
  `handoff_ac`。
- **端口**：`agv:SEMI_AB → handoff_ac:SEMI_AC`；`agv/station`。
- **设备/资源**：`arm_A`；`handoff_ac`、`dock_A`、`zone_ab`、`zone_ac`、
  `arm_A`。
- **工步**：`arm_pick_place`。
- **完成验证**：`unit_handoff_verified`；后继 `housing_finish`。
- **运行时任务**：`a_agv_uid{N}`；A 臂 + AGV 取料源。

### 3.5 `housing_finish`（旧 kind `c_handoff`）

- **语义**：C 从 `handoff_ac` 取 `SEMI_AC`，转换为 `SEMI_CE`，放到
  `line_ce` 入口，由 C→E 传送带送到 E。
- **端口**：`handoff_ac:SEMI_AC → line_ce:SEMI_CE`；`station/conveyor`。
- **设备/资源**：`arm_C`；`line_ce`、`handoff_ac`、`zone_ac`、`arm_C`。
- **前置**：`housing_direct_A` 或 `housing_alt_A`，`predecessor_policy=any`
  （两条壳体路线任一条完成即可）。
- **工步**：`arm_pick_place`。
- **完成验证**：`unit_handoff_verified`；后继 `housing_to_E_buffer`。
- **运行时任务**：`c_handoff_uid{N}`；C 臂 + handoff 取料源。

### 3.6 `housing_to_E_buffer`（旧 kind `e_conveyor`）

- **语义**：E 从 `line_ce` 停止区取 `SEMI_CE`，放到 `buffer_e_c`。
- **端口**：`line_ce:SEMI_CE → buffer_e_c:SEMI_CE`；`conveyor/station`。
- **设备/资源**：`arm_E`；`line_ce`、`buffer_e_c`、`arm_E`。
- **工步**：`conveyor_pickup` → `arm_pick_place`。
- **完成验证**：`unit_handoff_verified`；后继 `kit_join`（逻辑合流，不创建任务）。
- **运行时任务**：`e_conveyor_uid{N}`；E 臂 + line_ce。

### 3.7 `bracket_process`（旧 kind `d_conveyor`）

- **语义**：D 从 `line_s2d` 取 `RAW_D`，转换为 `PART_DE`，放到 D 的 AGV 托盘。
- **端口**：`line_s2d:RAW_D → agv:PART_DE`；`conveyor/agv`。
- **设备/资源**：`arm_D`；`line_s2d`、`dock_D`、`arm_D`。
- **工步**：`conveyor_pickup` → `arm_pick_place`。
- **完成验证**：`unit_handoff_verified`；后继 `transport_DE`。
- **运行时任务**：`d_conveyor_uid{N}`；D 臂 + AGV 托盘。

### 3.8 `transport_DE`（旧 kind `transport_de`）

- **语义**：AGV 载着 `PART_DE` 从 `dock_D` 行驶到 `dock_E`。
- **端口**：`agv:PART_DE → agv:PART_DE`；`agv/agv`。
- **设备/资源**：`agv_1`；动态 lanes/docks（东直道）。
- **工步**：`agv_route`。
- **完成验证**：`agv_route_verified`；后继 `bracket_to_E`。
- **运行时任务**：`transport_de_uid{N}`；`AGVRouteController4`。

### 3.9 `bracket_to_E`（旧 kind `e_agv`）

- **语义**：E 从 AGV 托盘取 `PART_DE`，放到 `buffer_e_d`。
- **端口**：`agv:PART_DE → buffer_e_d:PART_DE`；`agv/station`。
- **设备/资源**：`arm_E`；`buffer_e_d`、`dock_E`、`arm_E`。
- **工步**：`arm_pick_place`。
- **完成验证**：`unit_handoff_verified`；后继 `kit_join`。
- **运行时任务**：`e_agv_uid{N}`；E 臂 + AGV 取料源。

### 3.10 `kit_join`（旧 kind `logical_join`）

- **语义**：E 岛在 `buffer_e_c` 有 `SEMI_CE`、`buffer_e_d` 有 `PART_DE`
  时，原子消费两条父 UID，生成一个 `FINAL` 放到 `output_e`。
- **端口**：`buffer_e_c:SEMI_CE + buffer_e_d:PART_DE → output_e:FINAL`。
- **设备/能力**：`logic_E` / `logical_join`；不是物理设备。
- **工步**：`logical_join`。
- **完成验证**：`join_pair_committed`；前置 `housing_to_E_buffer` 和
  `bracket_to_E`，`predecessor_policy=all`（AND）。
- **运行时**：不创建 `Stage4Task`；由 `Stage4Coordinator._check_join` 调用
  `MaterialRegistry.commit_join`。缺件等待，重复/错型拒绝，父 UID 写入
  FINAL；不是机械臂装配。

## 4. 工序 → 任务/控制器映射

| 工序 | 旧 task kind | 运行时任务 | 控制器/执行路径 | 主要证据 |
|---|---|---|---|---|
| `housing_direct_A` | `a_conveyor` | `a_conveyor_uid*` | `Stage4UnitController(A)` | `TASK_*`、`MATERIAL_PROCESS/MOVE/PLACE` |
| `housing_alt_B` | `b_conveyor` | `b_conveyor_uid*` | `Stage4UnitController(B)` | 同上 + `LOAD_NOT_ON_TRAY` 检查 |
| `transport_BA` | `transport_ba` | `transport_ba_uid*` | `AGVRouteController4` | `ROUTE_START/DONE`、`LOAD_SLIP` |
| `housing_alt_A` | `a_agv` | `a_agv_uid*` | `Stage4UnitController(A)` | `AGV_TRAY_PICK`、`MATERIAL_*` |
| `housing_finish` | `c_handoff` | `c_handoff_uid*` | `Stage4UnitController(C)` | `MATERIAL_PROCESS/MOVE` |
| `housing_to_E_buffer` | `e_conveyor` | `e_conveyor_uid*` | `Stage4UnitController(E)` | `MATERIAL_MOVE/PLACE` |
| `bracket_process` | `d_conveyor` | `d_conveyor_uid*` | `Stage4UnitController(D)` | `MATERIAL_PROCESS/MOVE` |
| `transport_DE` | `transport_de` | `transport_de_uid*` | `AGVRouteController4` | `ROUTE_*`、`LOAD_SLIP` |
| `bracket_to_E` | `e_agv` | `e_agv_uid*` | `Stage4UnitController(E)` | `MATERIAL_MOVE/PLACE` |
| `kit_join` | `logical_join` | 无 | `_check_join` + `commit_join` | `MATERIAL_CONSUMED`、`JOIN_COMMIT`、`FINAL_CREATED` |

`Stage4UnitController` 的取料源由 `source_kind` 决定（conveyor/agv/station），
放置汇由 `sink_kind` 决定（station/agv/conveyor）；`AGVRouteController4` 只
处理 `agv_route` 工步；`kit_join` 不进入设备派工。

## 5. 文档设备 ↔ 场景设备

> CoppeliaSim alias。场景 alias 在启动时由 `Stage4Scene` 解析成 handle；
> handle 只存在于运行时，不写入产品工艺定义或持久证据。

### 5.5 资源/区域 vs 场景设备

- **设备**（`DeviceSpec`）是能力提供者；**资源**（`ResourceTable`）是互斥锁；
  **区域**（`ZoneSpec`/`MaterialRegistry`）是物料容量/位置。
- `arm_A` 同时是设备目录 ID 和资源 ID：前者提供 `robotic_pick_place`，后者
  表示臂运动包络互斥；字符串同名但用途不同，不能因为同名就认为是一个对象。
- `line_s1a` 同时是资源 ID 和物料区域 ID，但对应场景对象 `Conveyor_In`；
  三者不是同一概念。
- `dock_A` 是资源 ID，不是场景对象；`Sensor_AGV_Dock` 才是场景传感器。
- `arm_A` 是资源 ID，也是设备目录 ID；场景对象是 `Robot_UR5_01`。
- `logic_E` 是设备目录中的逻辑处理器，不是场景对象；它使用 E 缓冲/输出
  区域完成合流。
- `zone_ab`/`zone_ac`/`agv_lane_*` 没有场景对象，纯粹是调度资源。

## 6. 绑定、校验与变更约定

- 场景 alias 全部扁平下划线，不含 `/`；`getObject` 路径查询才使用 `/`。
  不要把 `~`、`/` 或路径写进 `DeviceSpec`/recipe。
- `Stage4Scene` 启动时通过 `UNIT_ALIASES`、`LINE_DEFS`、`TARGET_DUMMIES`
  等解析 `Stage4Unit` 的
  `island/robot/joints/suction/tcp/sensor/ik_target/station/place_target/
  dock_sensor`；控制器只拿 `UnitSceneView`/runtime 接口，不直接持有任意句柄。
- `REQUIRED_ALIASES`、`TARGET_DUMMIES` 和 `validate_contract` 检查
  alias 唯一性/契约；`build_contract_extra().layout.units[].aliases/targets`
  记录稳定映射。
- 修改场景 alias 或布局：更新 `simulation/config.py` 的 `UNIT_ALIASES`/
  `LINE_DEFS`/`HANDOFF_AC`/`E_BUFFERS`/`E_OUTPUT`/`REQUIRED_ALIASES`/
  `TARGET_DUMMIES`，重新派生/校验 v1 场景包，更新本文；当前
  `v1/L5_UFLOW/v001_20261103_004317` 受保护，不能原地改。
- 修改设备目录（`DeviceSpec`/`OperationTemplate`）：更新
  `default_process.py`，递增 `PROCESS_MODEL_VERSION`，运行
  `test_v1_process_model.py`/`test_v1_coordinator_process.py`；
  若 alias 未变，不需要重建场景包；后续派生场景包的 manifest 会记录新版本。
- 不要把 handle 写入持久产品工艺定义/证据；handle 只在启动绑定/runtime 中使用。
