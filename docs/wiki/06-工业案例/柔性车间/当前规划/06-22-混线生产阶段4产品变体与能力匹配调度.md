# 混线生产阶段 4：产品变体与能力匹配调度

## 实施状态（2026-11-04）

WP0–WP4 已在 v1 代码实现：runtime-backed 任务写入口收敛到
`OperationRuntime`、新增纯策略 `domain/scheduling.py`、coordinator 按决策
选定设备并原子申请资源。`full_flow` 实机验收通过（FINAL 1 件、父 UID
`[1,3]`、11 条调度决策可解释）。WP5（等价候选设备扩展）因没有经过动态
几何验证的第二候选而未实施；WP6（AGV 停靠/接触余量复核）未执行，原阈值
未放宽。测试与实机结论见 [[implementation/V1_STAGE4_REPORT]]。

## 目标

在阶段 3 的 recipe DAG 已能稳定执行后，扩展混批路线表达，并让调度器从 ready 工序的候选设备中选择当前可行者。当前 `ProcessCatalog` 已有静态 `CapabilitySpec`/`DeviceSpec` 和模板候选声明；本阶段实现的是把这些声明真正用于运行时筛选、资源检查和可解释派工，而不是重建能力目录。阶段核心是能力匹配，不是全局最优。

本页定义业务范围、调度原则和验收目标。文件级工作包、代码落点、输入输出契约、测试门槛、仿真证据和回退条件见 [[implementation/V1_STAGE4_SCHEDULER_PLAN]]；实施时按该方案的 WP0–WP6 顺序推进。

测试维护记录：目录校验中重复的未知引用和缺失字段负例已参数化，保留各输入的独立失败报告；不同语义的路线、循环和物料连通性负例仍分别保留。详见实施方案“现有目录负例的去重记录”。

## 场景业务定义

使用现有 L5_UFLOW 布局定义三个简单产品/半成品流：

- `housing_direct`: RAW_A 走 line_s1a → arm_A → handoff_ac → arm_C → line_ce。
- `housing_alternate`: RAW_B 走 line_s1b → arm_B → AGV B→A → arm_A → handoff_ac → arm_C → line_ce。
- `bracket`: RAW_D 走 line_s2d → arm_D → AGV D→E → arm_E 的 D buffer。
- `kit`: C 路径的 housing 与 D 路径的 bracket 按订单/配套键在 E 合流。E 当前仅逻辑生成 FINAL，场景不宣称有真实装配动作。

这是真实可表达的路线变体和混批交错，但当前 A 与 B 前段不是同一道工序的设备替代：它们是不同的工序子图，之后在 A/C 流程汇合。只有在业务定义明确“等价工艺且输出规格相同”后，才将多个 station 放进同一 operation 的候选设备集合。

## 能力匹配模型

operation 声明要求，例如 `robotic_pick_place`、特定负载区间、工具、物料尺寸/姿态范围、输入输出 zone、目标容差；device 声明能力及限制，例如 arm 工作区、工具、负载和支持的 source/sink 类型。候选集合按以下顺序过滤：

1. recipe 允许的候选设备集合。
2. 静态能力匹配和设备当前可用状态。
3. 场景绑定完整、相关目标对象存在。
4. 区域/物料到位、工序依赖和目标 buffer 容量满足。
5. `ResourceTable.acquire_all` 全量资源申请成功。
6. 运动控制器在真实目标姿态下 IK/碰撞/路径可行。

静态 capability 只用于缩小候选；planner 的运行时碰撞和可达检查才是最终依据。首轮 `full_flow` 中沿用当前已验证的设备分配，只验证能力声明和匹配记录；不人为构造不可达设备、设备故障或全候选拒绝场景。真实可替代设备的运行时重派需待有对应几何/路径验证后再单独加入。

## 调度策略迭代

首轮只实现确定性规则：当前批次/配套优先级 → 等待时间 → ready 时间 → 稳定 operation id。现有入口没有订单优先级对象，订单优先级字段仅在未来引入订单模型后启用。策略输入和决策输出必须可序列化并复现。每条派工 evidence 记录：候选设备、静态能力匹配结果、拒绝理由、资源申请结果、最终选择、仿真时间和策略版本；动态健康状态只有具备权威数据源后才进入筛选。

初期不因“同能力”就随意把 A/B/C 等机械臂互换。候选设备只能来自 recipe 明确允许的路线；arm 可达性还要通过该工件/场景的 target 与 collision runtime 检查。AGV 是共享的单设备，不能通过重复注册制造并行产能。

## 实施顺序

0. **先关闭已知状态写入口缺口。**将 recipe-backed `Stage4Task` 的 legacy 字段限制为只读投影；TaskQueue/coordinator 生命周期变更经 `OperationRuntime` 受控方法完成。加入直接赋值拒绝、正常排队/启动/完成仍能同步单一实例状态的测试。必要的 reposition 兼容写入只在明确的非 runtime-backed 边界保留。
1. 基于现有 `full_flow` 有限批次与静态 recipe 明确 route variant，不假设已存在订单对象，也不改变设备执行器。
2. 将 ready-set scheduler 从 coordinator 事件循环分离为纯策略对象；输入快照，输出候选排序，不写 CoppeliaSim。
3. 实现静态 capability / device status 筛选和设备占用；先固定路线候选。
4. 接入资源全量申请及 runtime feasibility；在 `full_flow` 正常输入下按固定候选执行。
5. 使用既有 `full_flow` 批次观察不同产品路线任务的交错运行，并检查 shared line/dock/zone 的互斥。
6. 仅当产品语义允许且各设备目标均已通过 IK/碰撞验证后，才增加一项多设备等价候选；本阶段先不加入故障触发的动态重派。阶段 2 的静态绑定完整性不视为其它机械臂几何可达验收；任何新候选须在实际目标姿态通过 IK、碰撞和路径验证。
7. 针对阶段 2–3 已暴露的物理基线风险，对 D→E 载货停靠与 E 放置链做一次 focused 复核，记录到站误差、载荷滑移及 pre-place 结果。仅当一次结果不足以区分波动与稳定问题时再增加重复；不要求分布统计。该调查独立于能力调度，不得放宽停靠、接触或安全阈值。
8. 从 `full_flow` events 重算吞吐、WIP、等待和并发工序指标，判断是否值得另立调度优化阶段。

## 验收

- `full_flow` 可交错运行 `housing_direct`、`housing_alternate`、`bracket`，最终配套数量和父 UID 正确；批次/订单抽象按阶段 3 实际入口定义。
- recipe-backed task 的旧字段无法绕过 `OperationRuntime` 任意改写；合法 coordinator/TaskQueue 生命周期仍只更新同一实例，且既有证据字段兼容。
- 当前 `full_flow` 设备选择符合 recipe 和设备能力目录；若尚无已验证的等价替代设备，不把动态替代派工列为本阶段完成条件。
- 静态设备绑定、动态几何验收分别报告；每个实际候选设备/目标组合都有 IK、碰撞和路径验证证据，未覆盖的组合明确标记未验收。
- 同一 recipe/order/scene seed 重跑时，派工序列可复现。
- 资源冲突时无部分持锁；相邻 arm/dock/line/lane 互锁语义不变。
- 运动风险有针对性复核记录；若未实施参数/算法改善，保留为独立后续风险，不改变当前安全阈值。
- 仿真端到端只运行 `full_flow`；其吞吐、任务等待、并发工序数量由事件可重算。不新增第二个仿真场景。

## 不在此阶段做

不做全局最优化、自动改变已开始工序、自动修改配方、任意设备间几何自动迁移、提高并发上限或移除碰撞/安全检查。
