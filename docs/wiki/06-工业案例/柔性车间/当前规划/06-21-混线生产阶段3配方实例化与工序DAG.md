## 目标

在已有静态 `RecipeSpec`/`OperationTemplate` 和单实例 `OperationInstance` 基础上，增量实现配方实例化、依赖 DAG、ready set 和工序解锁。当前系统没有独立订单对象；首个输入仍是 `full_flow` 配置的有限批次。阶段目标是默认工艺数据驱动复现现有流程，不做多产品动态选路优化。

## 工序与工步的边界

- **Recipe** 是产品/订单可复用的工艺模板。
- **OperationTemplate** 是 recipe 中的工序定义。
- **OperationInstance** 当前是任务所持有的单工序运行状态记录；本阶段扩展其关联订单/配方/依赖等上下文，使它成为工序 DAG 中可调度的实例。
- **WorkStepTemplate** 是工序内部可复用步骤，如 `wait_for_material`、`pick_place`、`verify_output`。
- **Executor state** 是工步运行细节，如机械臂 `APPROACHING/ATTACHING/LIFTING`；它被汇总为工序运行状态和证据，不创建独立生产单。

例如“UID 7 从 A 到 handoff_ac”是一道 Operation；其 arm executor 内部执行稳定性确认、approach、吸附、lift、transfer、place、release、验证等工步/状态。

## 最小数据模型

在不破坏现有证据兼容的前提下，逐步扩展 `OperationInstance` 关联：

```text
operation_instance_id, order_id, recipe_id, recipe_version
operation_template_id, selected_route, material_input_uids[]
predecessor_instance_ids[], capability_requirements, candidate_device_ids[]
source_zone, target_zone, resources[], priority
state, execution_id, current_work_step, timestamps, evidence, failure_reason
```

复用现有 `TaskStatus` (`PENDING`、`WAITING`、`RUNNING`、`BLOCKED`、`DONE`、`FAILED`、`REJECTED`) 作为迁移期生命周期，不立即引入平行枚举。设计映射时区分依赖未满足、资源等待、执行中和已完成等语义；确需更细状态时须统一迁移 TaskQueue、证据与兼容接口。`Stage4Task` 当前通过受控属性代理 `OperationInstance` 字段；DAG runtime 建成前继续由现有队列驱动，建成后逐步让 runtime 成为唯一工序状态所有者，禁止新旧状态双写。

## DAG 语义

- 顺序依赖：后继 operation 只在前驱成功并提交输出后 ready。
- 路线选择：订单实例化时选择一个 route variant，未选分支不生成可执行实例；共享尾段依赖 `selected_route.terminal`，不能误写成等待所有备选路线。
- AND 合流：E 配对要求两个指定输入谱系均已完成并在对应 buffer；配对验证成功后原子消费两个父输入、生成一个 FINAL 输出。
- OR 路由先作为订单释放时的静态选择；阶段 4 才基于候选设备/调度动态决策。
- 返工/循环在本阶段不开放；recipe DAG 必须无环。返工属于暂缓的后续异常恢复范围。
- executor 的 `SUCCEEDED` 只是物理动作完成；只有业务验证器与材料提交成功后 operation 才变成 `SUCCEEDED`，避免动作完成但物料账本未提交。

## 文件和流程

复用 `ProcessCatalog` 已有的静态目录/引用校验，扩展 `domain/operation_runtime.py` 及图实例化调用，新增针对实际实例图的依赖与输入输出校验；仅当现有模块职责不清或校验复杂度确有增长时再拆 `recipe_loader` / schema 模块。首版沿用项目内 Python 数据模型，不同时开放 YAML/JSON/Python 插件。图级校验覆盖无环、选定路线终点、实例前驱闭合、输入输出兼容和 join 输入完整性。

runner 启动后：

1. 加载并校验 recipe 与场景能力目录。
2. 以当前 `full_flow` 批次入口创建输入物料 UID 和运行批次上下文，按固定路线实例化 operation graph；订单实体可在需要产品订单语义时再引入。
3. scheduler/coordinator 查询 ready operations，并按当前固定设备选择规则申请资源。
4. executor 启动 operation 的 work-step sequence，并在每 tick poll。
5. 成功后运行 operation validator；将物料状态/区域/类型提交为一个逻辑事务，再解锁后继。
6. executor 成功后完成工序验证和物料提交；若底层返回失败，保留原有安全停止/失败语义，不自动返工、重试或改路线。本阶段不设计新的异常恢复流程。

## 实施顺序

### 代码级实施步骤

下面按提交顺序拆分。每一步先保持当前 `full_flow` 可运行，再由下一步接管相应职责；不要同时维护一份 DAG 状态和一份可独立变化的 `Stage4Task` 状态。

1. **固定实例化输入与实例 ID。**在 `domain/operation_runtime.py` 扩展运行时模型，不改静态 `RecipeSpec` 的职责。增加一次有限批次的运行上下文（例如 `RecipeRunContext`），只保存 `run_id`、`recipe_id`、`recipe_version`、入口物料 UID/类型/区域、每个入口选定的 `route_variant_id` 和创建时间；不引入可持久化订单/MES 实体。扩展 `OperationInstance`，保留现有 `instance_id/template_id/kind/uid/source/destination/device/state/evidence` 兼容字段，增加上述 recipe/run 标识、`predecessor_instance_ids`、`selected_route`、输入/输出 UID 列表及 `current_work_step`。实例 ID 使用确定性组合（如 `run_id:uid:operation_id`），保证不同 UID 的同一模板不冲突，也不依赖模板元组排列。更新 `as_dict()`，保留既有证据键不改名。

2. **实现实例图数据结构与校验。**在 `domain/operation_runtime.py` 加入轻量 `OperationGraph`（按 `instance_id` 索引实例，并提供模板/前驱/后继索引）和 `OperationRuntime`。实例化入口接收已校验的 `ProcessCatalog`、recipe、一个入口物料和明确的 route variant；按选中路线只实例化该路线的物理工序及共享后段。`full_flow` 的 `RAW_A` 入口映射 `housing_direct`，`RAW_B` 映射 `housing_alt`，`RAW_D` 映射 `bracket_route`；这是现有有限批次按入口条目固定路由，不是同一 UID 的备选路径同时实例化，也不做动态选路。路线共享尾段 `housing_finish` / `housing_to_E_buffer` 每个壳体 UID 只生成一次，前驱绑定到该 UID 实际选中的路线终点，不能把未选路线列为 AND 前驱。E join 的具体双 UID 由既有 `flow.pair_candidates()` 选出后，创建一个绑定这两个父实例的 join 节点；不要在批次图创建时猜测配对。对已实例化子图校验实例 ID 唯一、所有前驱均在图内、图无环、输入输出 UID/类型/区域可连接、选中路线恰有预期终点、join 两个输入端口各绑定一个匹配谱系；所有诊断包含 run/recipe/operation/instance 定位。目录静态校验仍由 `ProcessCatalog.validate()` 负责，不复制其能力/设备/资源检查。

3. **用 ready set 驱动解锁。**`OperationRuntime` 提供 `ready()`、`mark_started()`、`commit_success()`、`mark_failed()` 等窄接口。初始 ready 仅包含入口节点；非入口节点在其全部实际前驱为 `DONE` 且前驱输出已提交后进入 ready。对明确标为 OR 的共享尾段，只接受本实例选中的 route terminal；不得把“任一依赖 DONE”泛化到其他工序。ready 按稳定键（priority、创建序号/实例 ID）返回，避免 recipe 节点排列影响合法图的执行语义。保留 `TaskStatus`；依赖未满足的实例留在 runtime 的未解锁集合，不提前塞入 `TaskQueue` 标成 `WAITING`，资源申请失败才沿用队列的 `WAITING/BLOCKED`。失败前驱不解锁后继，不重试或改线。

4. **接到输入物料创建和 coordinator 生命周期。**在 `application/coordinator.py` 的 `_spawn_source()` 中保留现有 UID 创建、`MaterialRegistry`（场景句柄）/`flow`（物料谱系）登记及事件顺序；用入口模板和固定映射创建/取得该 UID 的图，再从 runtime ready 集合取首个实例并生成 `Stage4Task`。在 `domain/tasks.py` 让 `Stage4Task` 构造器可接收既有 `OperationInstance` 并直接代理它；`make_task_from_operation()` 负责把 runtime 实例投影为执行所需字段，禁止同时新建第二个 `OperationInstance`。coordinator 每 tick 先把 runtime 已 ready 且尚未入队的物理实例提交到现有 `TaskQueue`，然后复用阶段 2 executor 和原来的资源申请、`pre_tick → sim.step → post_tick` 流程；逻辑 `kit_join` 不进入 arm/AGV 派工。

5. **把完成提交与后继解锁接在同一成功边界。**在 `_commit_unit_result()` 保留现有 executor 完成后的位姿/类型/物理验证和 flow 区域提交；只有两者都成功后才调用 runtime `commit_success(instance_id, output_uids, evidence)`，然后派生 ready 后继。把 `FOLLOWUP` 的“模板 successor → 创建新 task”职责迁到 runtime；如需与旧流程对照，只在纯测试夹具中保留固定旧序列，不添加生产运行开关，也不允许两条路径在同次运行中都提交任务。按 UID 生成后继实例：`housing_alt_B → transport_BA → housing_alt_A → housing_finish`；直达路径为 `housing_direct_A → housing_finish`；之后均到 `housing_to_E_buffer`。物料区域变化和 output UID 写入成功提交记录，重复提交拒绝且不能再次释放后继。executor 的 `SUCCEEDED` 只触发验证，不能直接把 operation 标为 `DONE`。

6. **将 E join 纳入图 runtime，复用原子物料账本。**把 `_check_join()` 当前“扫描 `flow.pair_candidates()` 后直接 `flow.commit_join()`”改成 runtime join handler：当两类输入的工序父节点均完成且对应物料分别位于 `buffer_e_c`、`buffer_e_d` 时，按既有 `flow.pair_candidates()` 取得具体 UID，确认它们分别对应图中尚未消费的 `housing_to_E_buffer` 与 `bracket_to_E` 输出，再创建绑定两个父实例的 `kit_join` 节点。handler 沿用 `flow.commit_join()` 的 pair key、双父 UID 消费、FINAL UID 分配和重复配对拒绝；`MaterialRegistry` 仍只负责生成/删除仿真对象和句柄。不得在 coordinator/runtime 再实现一套配对选择或物料账本。账本返回成功后才将 join operation 标为 `DONE` 并记录 FINAL 输出/evidence；输入未就绪则不创建节点、不生成虚假的 `Stage4Task`。调整 `finished` / acceptance 汇总，让已实例化图中所有必需节点完成才算成功，同时维持既有事件、FINAL 数与物料证据字段。

7. **按运行路径逐段切换并删除旧生成器。**先给单 UID 直达支路做纯 Python runtime 测试，再把 `full_flow` 中 RAW_A→A→C→E 入口接入；核对 baseline 的事件序列、资源释放时机、UID/区域/谱系和任务状态。随后接入 RAW_B→B→AGV→A→C→E，再接入 RAW_D→D→AGV→E 和双输入 join。每条支路通过对应单测和完整既有测试后，删除 `_submit_followup()` 的生产调用及 coordinator 的静态 `successors` 推进逻辑；删除仅限已被 runtime 接管的逻辑，不删除 legacy `make_task()` 对 reposition/兼容测试所需的入口。最终只运行验收场景 `full_flow`，以阶段 0 基线证据比较结果，不新增 scenario、CLI 开关或异常注入流程。

## 验收

- 默认 recipe 生成的 operation graph 能表达直接路线、AGV 绕行路线、支架路线及 E 双输入合流。
- 图执行次序只由 dependencies 和所选 variant 决定；改变 YAML/JSON 条目排列不改变合法 DAG 语义（若数据格式支持无序节点）。
- 每个 output UID 与 input UID 的谱系、区域变更和 operation evidence 一致；join 双消费/重复提交被拒绝。
- 无效 recipe 配置在仿真启动前给出结构化诊断；这是静态输入校验，不属于异常场景测试。
- 默认流程只跑 `full_flow`；与阶段 0 基线相比，工序结果、FINAL 数、父 UID 和物料位置一致。其它场景和异常注入不作为阶段门槛。

## 不在此阶段做

不开放 UI 编辑、不支持任意用户代码、不做动态候选设备重派、复杂条件表达式、返工循环、CP-SAT 或数据库/MES 接入。

## 阶段完成后的跟踪项

- **旧字段写入口**：按 [[wiki/06-工业案例/柔性车间/当前规划/06-19-混线生产阶段0-1基线与静态工艺目录]] 的复核项，在 recipe-backed `Stage4Task` 上落实只读投影，并验证 coordinator/TaskQueue 只通过 runtime 生命周期接口更新状态。此项在阶段 4 接入能力筛选前完成。
- **验收边界**：本阶段只证明默认路线下的 `full_flow` 与图语义；未运行 `no_pair`、`staggered_batch` 或异常注入场景。若阶段 4 增加相应产品/批次语义，再为新增行为定义独立验收，不从当前证据外推。
- **物理运行余量**：AGV 停靠误差距阈值约 0.1–0.2 mm，重复运行曾伴随载荷偏移触发机械臂接触路径校验失败。该问题不归因于 DAG；后续应在阶段 4 的运动基线跟踪项评估重复性，不通过放宽安全阈值掩盖。
