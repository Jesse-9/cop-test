# 混线生产阶段 3：配方实例化与工序 DAG

## 目标

在已有静态 `RecipeSpec`/`OperationTemplate` 和单实例 `OperationInstance` 基础上，增量实现配方实例化、依赖 DAG、ready set 和工序解锁。当前系统没有独立订单对象；首个输入仍是 `full_flow` 配置的有限批次。阶段目标是默认工艺数据驱动复现现有流程，不做多产品动态选路优化。

## 工序与工步的边界

- **Recipe** 是产品/订单可复用的工艺模板。
- **OperationTemplate** 是 recipe 中的工序定义。
- **OperationInstance** 当前是任务所持有的单工序运行状态记录；本阶段扩展其关联订单/配方/依赖等上下文，使它成为工序 DAG 中可调度的实例。
- **WorkStepTemplate** 是工序内部可复用步骤，如 `wait_for_material`、`pick_place`、`verify_output`。
- **Executor state** 是工步运行细节，如机械臂 `APPROACHING/ATTACHING/LIFTING`；它被汇总为工序运行状态和证据，不创建独立生产单。

例如“UID 7 从 A 到 handoff_ac”是一道 Operation；其 arm executor 内部执行稳定性确认、approach、吸附、lift、transfer、place、release、验证等工步/状态。

## 最小数据模型

在不破坏现有证据兼容的前提下，逐步扩展 `OperationInstance` 关联：

```text
operation_instance_id, order_id, recipe_id, recipe_version
operation_template_id, selected_route, material_input_uids[]
predecessor_instance_ids[], capability_requirements, candidate_device_ids[]
source_zone, target_zone, resources[], priority
state, execution_id, current_work_step, timestamps, evidence, failure_reason
```

复用现有 `TaskStatus` (`PENDING`、`WAITING`、`RUNNING`、`BLOCKED`、`DONE`、`FAILED`、`REJECTED`) 作为迁移期生命周期，不立即引入平行枚举。设计映射时区分依赖未满足、资源等待、执行中和已完成等语义；确需更细状态时须统一迁移 TaskQueue、证据与兼容接口。`Stage4Task` 当前通过受控属性代理 `OperationInstance` 字段；DAG runtime 建成前继续由现有队列驱动，建成后逐步让 runtime 成为唯一工序状态所有者，禁止新旧状态双写。

## DAG 语义

- 顺序依赖：后继 operation 只在前驱成功并提交输出后 ready。
- 路线选择：订单实例化时选择一个 route variant，未选分支不生成可执行实例；共享尾段依赖 `selected_route.terminal`，不能误写成等待所有备选路线。
- AND 合流：E 配对要求两个指定输入谱系均已完成并在对应 buffer；配对验证成功后原子消费两个父输入、生成一个 FINAL 输出。
- OR 路由先作为订单释放时的静态选择；阶段 4 才基于候选设备/调度动态决策。
- 返工/循环在本阶段不开放；recipe DAG 必须无环。返工属于暂缓的后续异常恢复范围。
- executor 的 `SUCCEEDED` 只是物理动作完成；只有业务验证器与材料提交成功后 operation 才变成 `SUCCEEDED`，避免动作完成但物料账本未提交。

## 文件和流程

复用 `ProcessCatalog` 已有的静态目录/引用校验，扩展 `domain/operation_runtime.py` 及图实例化调用，新增针对实际实例图的依赖与输入输出校验；仅当现有模块职责不清或校验复杂度确有增长时再拆 `recipe_loader` / schema 模块。首版沿用项目内 Python 数据模型，不同时开放 YAML/JSON/Python 插件。图级校验覆盖无环、选定路线终点、实例前驱闭合、输入输出兼容和 join 输入完整性。

runner 启动后：

1. 加载并校验 recipe 与场景能力目录。
2. 以当前 `full_flow` 批次入口创建输入物料 UID 和运行批次上下文，按固定路线实例化 operation graph；订单实体可在需要产品订单语义时再引入。
3. scheduler/coordinator 查询 ready operations，并按当前固定设备选择规则申请资源。
4. executor 启动 operation 的 work-step sequence，并在每 tick poll。
5. 成功后运行 operation validator；将物料状态/区域/类型提交为一个逻辑事务，再解锁后继。
6. executor 成功后完成工序验证和物料提交；若底层返回失败，保留原有安全停止/失败语义，不自动返工、重试或改路线。本阶段不设计新的异常恢复流程。

## 实施顺序

1. 定稿 model/schema，以代码内默认 recipe 表达一个小的纯 Python 测试图。
2. 写 validator 正例与负例：当前默认图、重复 ID、cycle、未知能力、缺少 join 输入、类型不匹配、无终点。
3. 实现 graph instantiation 和 ready set；测试 route variant 只生成一条路径、AND join 等两输入。
4. 将 E join 迁为 operation runtime 的 join executor + validator；保留现有谱系提交原子性。
5. 将单 UID 的 S1→A→C 小流程接入 recipe runtime，比较事件序列和老流程。
6. 接通 B→AGV→A 及 D→AGV→E，运行唯一端到端仿真场景 `full_flow`；结果等价后删除 `FOLLOWUP` 运行时生成逻辑。

## 验收

- 默认 recipe 生成的 operation graph 能表达直接路线、AGV 绕行路线、支架路线及 E 双输入合流。
- 图执行次序只由 dependencies 和所选 variant 决定；改变 YAML/JSON 条目排列不改变合法 DAG 语义（若数据格式支持无序节点）。
- 每个 output UID 与 input UID 的谱系、区域变更和 operation evidence 一致；join 双消费/重复提交被拒绝。
- 无效 recipe 配置在仿真启动前给出结构化诊断；这是静态输入校验，不属于异常场景测试。
- 默认流程只跑 `full_flow`；与阶段 0 基线相比，工序结果、FINAL 数、父 UID 和物料位置一致。其它场景和异常注入不作为阶段门槛。

## 不在此阶段做

不开放 UI 编辑、不支持任意用户代码、不做动态候选设备重派、复杂条件表达式、返工循环、CP-SAT 或数据库/MES 接入。
