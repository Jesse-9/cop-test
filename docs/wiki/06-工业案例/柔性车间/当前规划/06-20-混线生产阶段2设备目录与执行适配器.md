# 混线生产阶段 2：设备目录与执行适配器

## 目标

在阶段 0–1 已有 `ProcessCatalog` 静态设备/能力声明的基础上，逐步将应用协调与 CoppeliaSim 执行实现隔离。工作重点是包装现有机械臂、AGV 和逻辑合流调用，并建立稳定 ID 到 scene/runtime 对象的绑定；不重复创建 `DeviceSpec`/`CapabilitySpec` 目录。调度仍使用当前默认工艺和固定候选设备。

v1 代码上的文件级实施方案、接口契约、测试矩阵与版本处置见 [[implementation/V1_STAGE2_EXECUTOR_PLAN]]；本文只保留阶段目标与验收，不重复代码清单。

## 设备范围与建模

| 对象 | Device ID 示例 | 能力/接口 | 资源语义 |
|---|---|---|---|
| UR5 单元 | `arm_A`…`arm_E` | `robotic_pick_place`；启动取放、逐 tick 查询；沿用现有安全停止 | arm、相邻臂 zone、所需源/目标区 |
| Pioneer AGV | `agv_1` | `agv_transport`；按 route spec 行驶、报告停靠/阻塞 | 实际 lanes、dock、AGV 本体 |
| 传送带 | `line_s1a`、`line_ce` 等 | 当前是仿真设备/线资源，由已有控制逻辑启停；尚无通用逐 UID 执行器 | line 和取放区 |
| 逻辑工序处理器 | `operation handler` | `logical_kit_join`；校验父件并返回配对结果，不是物理设备 | 由 operation runtime 串行化输入/输出提交 |
| 传感器/交接位 | `sensor_*`、`handoff_ac` | 查询能力或位置状态；一般不作为生产 executor | 观测设备本身可共享；区域以容量资源表示 |

设备目录中的 ID 是工程稳定标识，不是 CoppeliaSim handle。继续复用现有 scene contract / alias 启动校验并解析实际 handle；本阶段不另造一套场景发现机制。recipe 只保存 ID、语义目标和 zone。

本阶段采用“**全部实例做静态绑定核对，按执行实现选代表设备做动态验证**”的覆盖原则。五台 UR5 共用同一控制器实现，因此动态机械臂验证只选一台代表（建议 `arm_A`）；但五台臂各自的 alias、IK/TCP/吸盘/碰撞 runtime 绑定和配置仍须全部通过场景契约核对。AGV 是独立执行实现，必须另测；传送带和 E 逻辑合流按各自接口做针对性验证。代表测试用于证明复用实现接通，不宣称所有物理工位的几何可达性均已重新验收。

## 接口与代码落点

代码从 `src/flexible_factory/` 现有边界演进：静态声明留在 `domain/process_model.py` / `domain/default_process.py`；CoppeliaSim alias/handle 绑定留在 `simulation/scene.py`、`simulation/contract.py` 及相关 runtime；应用编排目前在 `application/coordinator.py`。只有当包装控制器能减少真实耦合时才建立 executor/adapter 模块，且必须满足 `domain` 不导入 `simulation`、`simulation` 不导入 `application`。不得在 `src/stage4/` 建平行目录。

设备当前占用从活动执行和资源表推导，不另维护可漂移的 `BUSY` 镜像；只有设备健康/禁用状态有独立来源时才单独建模：

- `ArmExecutor` 包装 `Stage4UnitController`，负责构造控制器、调用 `pre_tick/post_tick`、映射完成/失败和读取安全锁存证据。
- `AgvExecutor` 包装 `AGVRouteController4` 与当前 reposition / transport 生命周期。
- 传送带当前作为共享线资源和底层 motor command facade，由现有 arm operation 在需要时控制 run/stop；本阶段不虚构按 UID 输送 executor 或 `conveyor_transport` capability。
- E 配对不是新增的设备 executor：继续由 coordinator 调用
  `MaterialRegistry.pair_candidates()` 完成候选选择，并沿用当前配对校验、输出生成
  与材料谱系提交边界。阶段 2 不复制候选选择规则，也不新增 `LogicExecutor`。

统一异步接口采用 tick 驱动：

```python
start(request: ExecutionRequest) -> execution_id
poll(execution_id) -> RUNNING | SUCCEEDED | FAILED
```

`ExecutionRequest` 是 coordinator 传给 adapter 的运行时请求，至少携带
`device_id`、运行时任务上下文、可选 `OperationTemplate`、任务/物料标识和
仿真时间；AGV 请求另带 `RouteSpec` 或等价 route intent。这样机械臂 adapter
可以装配 `Stage4UnitController` 所需 task/resources 上下文，AGV adapter 可以
表达载货运输和空载 reposition。reposition 使用 coordinator 创建的运行时任务，
adapter 不临时拼造另一种任务。请求不作为持久化 recipe/evidence 直接序列化；
稳定 ID 与 route intent 可记录，运行时任务对象及 CoppeliaSim handle 不外泄。

层级上，工序是配方和调度编排的业务模块；工序分配到具体设备后形成运行时任务，
设备侧再按控制器流程执行一个或多个工步。adapter 管理该任务的完整启动、逐 tick
推进和完成报告。仿真 tick 只是时间推进单位，不等于工步；阶段 2 不把每个低层
机械动作拆成独立调度任务。

`can_accept` 与 `capabilities` 可在目录中提供，执行可行性仍由具体 planner/controller 再确认。首版不实现 cancel/recovery 协议；正常的输入/资源等待由工序 runtime 处理。接口不得把物料 registry 的写入责任交给 executor；executor 报告执行证据，operation runtime/coordinator 验证后原子提交输出与区域。`FAILED` 仅用于避免把底层失败误报为成功，不扩展异常恢复策略。

## CoppeliaSim 执行约束

- 保持一个 Python stepping owner 和一个 `sim.step()` 调用点。运行循环继续由 coordinator 按 `pre_tick → sim.step → post_tick → reconcile` 推进。
- `start()` 不得同步阻塞到动作完成；`poll()` 每 tick 检查控制器状态。超时用 `sim.getSimulationTime()`，wall-clock watchdog 仍由 runner 管理。
- 同一仿真时刻按确定顺序下发写操作；不为每台设备开并发线程或并行 remote client 去写同一 joint/object。
- UR5 继续走现有 IK、路径规划、碰撞检查、吸盘、物理属性恢复和安全锁存；禁止用直接 set pose 替代动作控制。
- AGV 继续走 route graph / wheel controller；executor 提供 route intent，不直接让 recipe 写轮速。
- 句柄只存在启动绑定/运行时对象中；序列化 recipe、event 和 evidence 使用稳定 device/zone/alias 标识。

## 实施顺序

1. **核对静态映射。**以 `ProcessCatalog`、`default_process`、scene contract 和 `full_flow` 使用清单为准，列出所有相关设备 ID 到 scene/runtime 对象、资源和区域的对应关系。完整核对五台机械臂、AGV、相关传送带、传感器、dock 和 buffer；只补实际缺失的绑定，不重建静态目录。
2. **确定最小验证入口。**建立仅供测试调用的设备验收 harness（测试 helper 或内部 callable），复用现有场景工件、`build_components_v1`、scene contract 和控制器构造方式。测试专用 setup 注入一条正常任务并抑制来源生成与 join；harness 通过 `coordinator.step()` 推进，唯一 `sim.step()` 仍由 coordinator 持有，测试不自行驱动仿真。不开启 `full_flow`，不新增面向用户的运行模式、生产 scenario 或 CLI 参数。若复用现有生命周期组件必须初始化全部影子臂/碰撞集合，仍只启动一台代表机械臂执行动作。
3. **接入并验证机械臂 adapter。**包装 `arm_A` 的一个正常抓取/放置工序，验证 `start` 返回后不阻塞、多个 tick 后得到成功、保留完成证据、资源释放，且物料只在既有验证/提交边界更新。其余 `arm_B`…`arm_E` 不重复跑同样动作，但须通过第 1 步的静态绑定与配置核对。
4. **接入并验证 AGV adapter。**选一条最短且可重复的正常运输路线（例如 `dock_B → dock_A`），验证路线启动、逐 tick 推进、到站证据和资源释放。若载货运输与空载 reposition 走不同生命周期分支，则在同一代表路线测试中分别覆盖这两种正常请求；不要求重复执行全部 dock 组合。
5. **核对辅助设备边界。**通过既有测试验证传送带 run/stop 与状态读取仍受工序和 line resource 控制，不把它升级成逐 UID executor。E join 沿用 coordinator 与 `MaterialRegistry.pair_candidates()` 的既有候选选择和提交实现，不另建逻辑 executor 或重复实现配对规则；必要时复用既有 join 测试。传感器、dock 和 buffer 的全量静态映射由第 1 步覆盖。
6. **统一协调接入并做定向复验。**coordinator 经 adapter 启动/轮询代表 arm 与 AGV；纯单元测试确认状态和证据映射，focused CoppeliaSim 测试确认真实控制器/API tick 路径，检查适配器没有调用 `sim.step()` 或重复提交物料/资源状态。

每一步完成后删除已被 adapter 取代的重复调用分支；未迁移路径保留原调用，以小步替换现有协调逻辑。focused harness 只服务阶段 2 的代表设备验收，不成为生产运行入口；完整混线工艺仍由阶段 3 接入配方 DAG 后的 `full_flow` 端到端测试验收。

## 验收

- 全部 `full_flow` 后续所需设备 ID、alias、目标、资源与区域映射通过静态场景契约核对；该项不要求每台设备都执行一次物理动作。
- 一台代表机械臂（建议 A）完成一个正常工序的 focused CoppeliaSim 验证；其余机械臂实例通过完整绑定/配置核对，不声称其余工位的动作几何被重新验收。
- 一条代表 AGV 正常路线通过 focused CoppeliaSim 验证；必要时在同一路线测试中覆盖载货运输和空载 reposition 两种生命周期分支。
- conveyor 命令/观测边界通过针对性纯测试或现有组件测试；E join 继续由现有 coordinator/material registry 实现和既有测试覆盖，不将逻辑 handler 当作物理设备测试。
- 单元测试验证正常 `RUNNING → SUCCEEDED` 生命周期及完成证据映射；本阶段不新增异常注入、`BLOCKED/resume`、故障恢复或 cancel 测试，既有阻塞行为与回归保持不变。
- focused harness 只有一个 stepping owner；adapter 不调用 `sim.step()`，不双重修改 material registry、工序状态或 resource ownership。
- 本阶段**不要求运行 `full_flow`**；配方 DAG、B/D 多路线交错和 E 配对的端到端正确性在阶段 3 通过 `full_flow` 验收。

## 不在此阶段做

不做按能力动态选择替代工位、不让用户写配方、不建每设备独立生产调度器、不实现多线程 API、不改变运动算法或资源互锁、不做传感器视觉识别。当前固定候选设备是阶段 2 的范围边界；阶段 3 配方 DAG 稳定后，再单独规划能力驱动派工：由工序声明所需能力与候选设备，调度器结合设备可用性、资源和路线约束选择执行设备，executor 继续负责所选设备的执行生命周期。
