# 混线生产阶段 2：设备目录与执行适配器

## 目标

让工序通过设备 ID 和能力要求提交执行请求，由设备目录提供静态能力与运行状态，由适配器连接现有控制器。阶段结束时 `full_flow` 涉及的可执行单元（机械臂、AGV、逻辑工序处理器）经统一生命周期接口报告结果；传送带仍通过共享资源和 motor command facade 控制，传感器仍提供观测。调度继续按阶段 1 的默认工艺和固定候选设备运行。

## 设备范围与建模

| 对象 | Device ID 示例 | 能力/接口 | 资源语义 |
|---|---|---|---|
| UR5 单元 | `arm_A`…`arm_E` | `robotic_pick_place`；启动取放、逐 tick 查询；沿用现有安全停止 | arm、相邻臂 zone、所需源/目标区 |
| Pioneer AGV | `agv_1` | `agv_transport`；按 route spec 行驶、报告停靠/阻塞 | 实际 lanes、dock、AGV 本体 |
| 传送带 | `line_s1a`、`line_ce` 等 | run/stop、读取速度；可选按 UID 到区输送 | line 和取放区 |
| 逻辑工序处理器 | `operation handler` | `logical_kit_join`；校验父件并返回配对结果，不是物理设备 | 由 operation runtime 串行化输入/输出提交 |
| 传感器/交接位 | `sensor_*`、`handoff_ac` | 查询能力或位置状态；一般不作为生产 executor | 观测设备本身可共享；区域以容量资源表示 |

设备目录中的 ID 是工程稳定标识，不是 CoppeliaSim handle。继续复用现有 scene contract / alias 启动校验并解析实际 handle；本阶段不另造一套场景发现机制。recipe 只保存 ID、语义目标和 zone。

## 接口与代码落点

建议新增 `src/stage4/devices.py`：`DeviceSpec`、`CapabilitySpec`、设备目录和场景绑定。新增 `src/stage4/executors/`，但按真实需要建立模块，不创建空壳。设备当前占用从活动 execution 和资源表推导，不另维护可漂移的 `DeviceStatus.BUSY` 镜像；只有设备健康/禁用状态有独立来源时才单独建模：

- `ArmExecutor` 包装 `Stage4UnitController`，负责构造控制器、调用 `pre_tick/post_tick`、映射完成/失败和读取安全锁存证据。
- `AgvExecutor` 包装 `AGVRouteController4` 与当前 reposition / transport 生命周期。
- 传送带当前作为共享线资源和底层 motor command facade，由现有 arm operation 在需要时控制 run/stop；本阶段不虚构按 UID 输送 executor 或 `conveyor_transport` capability。
- `ProcessExecutor` 承载无运动逻辑工序，例如当前 E 配对；返回校验结果，由 operation runtime/coordinator 原子提交材料谱系。

统一异步接口采用 tick 驱动：

```python
start(operation, device_id) -> execution_id
poll(execution_id) -> RUNNING | SUCCEEDED | FAILED
```

`can_accept` 与 `capabilities` 可在目录中提供，执行可行性仍由具体 planner/controller 再确认。首版不实现 cancel/recovery 协议；正常的输入/资源等待由工序 runtime 处理。接口不得把物料 registry 的写入责任交给 executor；executor 报告执行证据，operation runtime/coordinator 验证后原子提交输出与区域。`FAILED` 仅用于避免把底层失败误报为成功，不扩展异常恢复策略。

## CoppeliaSim 执行约束

- 保持一个 Python stepping owner 和一个 `sim.step()` 调用点。运行循环继续由 coordinator 按 `pre_tick → sim.step → post_tick → reconcile` 推进。
- `start()` 不得同步阻塞到动作完成；`poll()` 每 tick 检查控制器状态。超时用 `sim.getSimulationTime()`，wall-clock watchdog 仍由 runner 管理。
- 同一仿真时刻按确定顺序下发写操作；不为每台设备开并发线程或并行 remote client 去写同一 joint/object。
- UR5 继续走现有 IK、路径规划、碰撞检查、吸盘、物理属性恢复和安全锁存；禁止用直接 set pose 替代动作控制。
- AGV 继续走 route graph / wheel controller；executor 提供 route intent，不直接让 recipe 写轮速。
- 句柄只存在启动绑定/运行时对象中；序列化 recipe、event 和 evidence 使用稳定 device/zone/alias 标识。

## 实施顺序

1. 先实现 `DeviceSpec` 和只读目录，枚举五臂、AGV、四条物流线及关键传感器/区域；E 逻辑配对登记为软件 operation handler。
2. 抽出 arm executor，跑一个 A 直达任务，验证正常启动、tick 推进、完成证据和资源释放。
3. 抽出 AGV executor，覆盖 `full_flow` 实际经过的载货路线和所需空载调位。
4. 通过最薄的 motor command facade 包装 conveyor 命令与状态读取，确认行为仍受当前工序和 line resource 控制。
5. 包装 E join，明确 executor 只计算/报告可提交结果，coordinator 仍拥有物料提交事务。
6. 统一 coordinator 对 executor 的启动、轮询和生命周期回调，再让默认 recipe 经统一入口运行。

每一步完成后删除已迁移的重复控制器调用分支；未迁移的设备路径保留原调用，避免 big-bang 重写。

## 验收

- `full_flow` 所需设备 ID 能通过现有 scene contract 正常绑定；不新增故障注入或异常场景来测试绑定失败。
- executor 单元测试只覆盖正常 RUNNING→SUCCEEDED 状态推进及完成证据映射；不新增异常注入、底层失败映射或恢复测试。
- 唯一仿真端到端验收为 `full_flow`；设备动作仍由原控制器完成，最终物料和配对结果正确。
- `sim.step()` 仍只有一个生产循环所有者；无 executor 直接推进 stepping。
- executor 不双重修改 material registry、工序状态或 resource ownership。

## 不在此阶段做

不做按能力动态选择替代工位、不让用户写配方、不建每设备独立生产调度器、不实现多线程 API、不改变运动算法或资源互锁、不做传感器视觉识别。
