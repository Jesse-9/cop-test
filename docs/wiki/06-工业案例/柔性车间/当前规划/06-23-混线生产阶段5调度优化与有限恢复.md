# 混线生产后续阶段：调度优化与异常恢复（暂缓）

> 当前实施范围只运行 `full_flow`，暂不考虑异常注入、故障恢复或调度优化。本页保留为后续需求清单，不是当前阶段承诺，也没有当前验收要求。恢复实施前应先基于当时的代码、设备能力和用户目标重新审查本页。

## 目标

在配方执行和能力匹配稳定后，加入订单交期、设备故障、换型/准备时间、缓冲 WIP 和可恢复阻塞；调度器可以重新安排**尚未启动**的工序。正在执行的机械臂轨迹或 AGV 路线不得被排程器擅自抢占。

## 先做可观测，再做策略

先确认现有 events 能稳定重算：每订单完工时间、operation cycle/wait/block、设备 busy/idle、buffer peak WIP、AGV distance/route time、due-date tardiness、重派次数和失败原因。建立固定订单集和随机种子对照。若没有这些数据，不添加看似高级的优化器。

设备状态至少区分 `AVAILABLE`、`BUSY`、`BLOCKED`、`FAULTED`、`MAINTENANCE`、`OUT_OF_SERVICE`。状态转换来自 executor/scene diagnosis 的证据；未知状态应阻止新派工并产生明确告警事件，而不是当作空闲。

## 有限恢复语义

- 未启动 operation 若设备故障：释放尚未执行的预留，在 recipe 允许范围内重新评估候选设备。
- 已经 RUNNING 的动作故障：交由 executor 安全停止并报告 material pose/attachment/velocity；先核实物料和设备状态，再由 coordinator 决定 BLOCKED、FAILED 或进入人工恢复流程。
- 仅当物料所有权、吸附状态、目标区、设备安全状态和资源 owner 均确认一致时，才允许从明确 checkpoint 续作。
- 自动重试有按工步/工序声明的次数上限和幂等性前置条件；不重放 attach/release 等可能重复产生物理副作用的动作。
- 返工不是把 FAILED 改回 RUNNING；建立新的返工 OperationInstance，并保留原工序失败谱系与订单审计。
- 资源释放遵循实际执行状态：动作中不能为“清理锁”而提前释放仍受物理实体占用的共享空间。

## 调度代价

由简单到复杂逐个加入：

1. 订单静态优先级与 due time。
2. waiting aging，避免低优先级饥饿。
3. 设备队列长度和预计工序时长。
4. 换型/setup 代价与工具状态。
5. AGV route time、line/dock/buffer 争用和预计 WIP。
6. 故障风险或剩余可用时间（仅当仿真能可靠表达）。

先用可解释、确定性的打分规则，并把每项代价分解写入派工记录。只有规则策略在固定数据集上呈现稳定不足，才评估 CP-SAT/MILP 等方案；优化器只产出候选计划，最终派工仍需过能力、前置条件、碰撞/可达性和资源验证。

## 实施顺序

1. 扩充 metrics/events，加入订单 due time、设备状态变更、候选重派原因和 WIP 指标。
2. 加入 AVAILABLE/BUSY/FAULTED 等设备状态和只对 READY/未预留工序的局部 re-dispatch。
3. 在模拟设备故障场景验证工序改派；先测未启动 arm 工序，再测 AGV 尚未启动的运输。
4. 为已运行的单类动作设计安全停机和现场核验；初期核验通过仍可选择标为 FAILED 并等待人工恢复。
5. 仅在能证明动作幂等、checkpoint 完整的路线增加 resume；把超时、重试次数、物料与资源核验作为 recipe policy。
6. 添加返工分支的最小例子（如质量检查失败后回到一个明确工位）；限制返工次数并保留原/返工工序关联。
7. 对固定混批样本比较 FIFO、priority/aging、带 setup/duedate 的策略；再决定是否部署优化求解器。

## 验收

- READY 工序可在其预选设备故障时转派到另一合法候选；RUNNING 工序不会被排程器静默抢占。
- 注入设备故障、AGV 阻塞、buffer 满和传送带故障时，系统状态与 UI/证据能够说明物料、工序和资源 owner。
- 每条恢复路径覆盖恢复成功、恢复条件不满足、超时和重复执行保护；不满足条件时保留现场并停止相关作业。
- 不存在资源泄漏、重复消费/生产 UID、重复 FINAL、失败工序被标为成功、订单永久无状态等问题。
- 调度指标基于事件重算，并在同一固定输入上比较策略的交期、吞吐、WIP、等待和可解释性。

## 不在此阶段默认引入

不默认加入多 AGV、分布式 MES/PLC、在线学习或黑箱策略、任意 Python recipe hook、无上限重试、自动修改物理现场、全局最优性承诺。若后续需求明确，再单独评估接口、验证成本和新增故障模式。
