# 混线生产阶段 5：调度优化与有限恢复

> 状态：暂缓，不表示已授权实施。本文将阶段 5 拆成可单独立项和验收的工作包；重新启动时先选一个具体业务用例，按门槛逐包推进。当前阶段 0–4 验收范围仍只有 `full_flow`，没有故障恢复验收。

## 1. 当前代码基线与缺口

截至 2026-11-05，阶段 4 报告记录 450 项纯逻辑测试通过、3 项仿真测试跳过，以及一次 `full_flow` 仿真通过：12 个工序实例完成、11 条物理派工决策选中 recipe 候选、资源清零。AGV 到站误差仍接近 `0.02 m` 门槛；此结果不证明运动重复性已经稳定。见 [[implementation/V1_STAGE4_REPORT]]。

| 能力 | 当前实现 | 阶段 5 需要补齐 |
|---|---|---|
| 派工 | `domain/scheduling.py` 对 ready 工序做确定性候选筛选；`coordinator.py` 记录 `SCHEDULE_DECISION` / `SCHEDULE_WAIT`，资源由 `ResourceTable.acquire_all()` 原子申请 | 没有业务订单 due time、设备健康事实源、setup 状态或基于这些字段的评分 |
| 运行状态 | `OperationRuntime` 有 `PENDING`、`WAITING`、`RUNNING`、`BLOCKED`、`DONE`、`FAILED` 迁移；已有阻塞/恢复窄接口 | `mark_resumed()` 表示同一执行继续运行，不含现场核验或 checkpoint 协议 |
| 资源与失败 | `ResourceTable` 有 owner、等待、全量申请和释放；coordinator 有超时及 freeze/abort 路径 | freeze 路径是停止/失败收敛路径，不是可复用的恢复事务；释放资源前必须确认物理占用已安全解除 |
| 指标 | `domain/metrics.py` 从任务事件重算处理、等待、阻塞、吞吐和设备利用率；WIP 由报告调用方传入 | 没有订单交期、setup、设备状态变更或策略比较指标；不能把现有 WIP 数字当作可预测的排程输入 |
| 改派 | 工序实例可记录选择设备；启动后禁止更改选择 | 未启动但已 claim/入队的工序也没有撤销选择、撤销队列投影并重新选择的完整生命周期 |
| 故障恢复 | 控制器和 AGV 执行器报告动作结果；失败路径冻结，不宣称自动恢复 | 缺少权威设备健康源、现场安全确认和满足幂等条件的续作协议 |

## 2. 激活门槛

开始任何阶段 5 代码变更前，立项记录必须给出：

1. 一个明确的业务问题及可观测结果，例如“arm_A 不可用时，将尚未启动且 recipe 允许的工序派给已验证的 arm_B”。没有第二个已验证候选时，不做设备故障改派。
2. 已选阶段 4 工件、固定输入与 seed、运行命令、基线 evidence，以及业务指标和比较口径。先复核 AGV 停靠/接触余量风险；若目标场景不能稳定完成，先处理该基线问题，不把运动失败混入排程效果。
3. 本轮唯一故障类型、允许恢复的状态、恢复责任方和人工介入点。第一轮不得同时承诺 arm/AGV/传送带/buffer 全类故障。
4. 要启用 due time、setup、资源容量或设备健康时，明确其权威输入及更新时间。没有数据源的字段不得伪造默认值参与派工。

任一项未明确时，只允许补充需求/基线证据，不开始对应运行时能力。每个工作包独立合并和验收；未通过其门槛，不进入依赖它的包。

## 3. 实施包

### WP0：冻结试验基线与范围

**落点：**更新本页对应的实施记录或新增 `docs/implementation/V1_STAGE5_PLAN.md`；复用 `docs/implementation/evidence/` 的裁剪证据格式。此包不改生产代码。

1. 选定一个操作、一个目标设备故障条件和一个固定输入批次；说明哪些工序已进入 `RUNNING` 时不得改派。
2. 固定当前 `full_flow` 的 scene artifact、config/layout digest、随机 seed、仿真版本、命令和有效 evidence。记录现有阶段 4 报告中的路线余量限制。
3. 定义基准指标和预期方向；至少包含完成数/父 UID、仿真完工时间、工序等待/阻塞时间、资源峰值占用和重派原因。

**通过门槛：**另一位维护者能按记录复现基线，且新场景只增加本包选定的故障变量。未通过则停止阶段 5 实施。

### WP1：补齐可重算的调度观测

**落点：**优先扩展 `domain/metrics.py`、`application/coordinator.py` 的事件 detail 和 `tests/test_v1_metrics_contract.py`；只加入 WP0 用例需要的字段。

1. 定义稳定的 `order_id`/`due_time` 来源；若当前入口没有订单实体，则由固定试验输入显式提供，避免先造通用订单系统。
2. 派工事件记录输入快照摘要、候选拒绝/延后原因、选中设备、资源 owner、策略版本及策略各项分值。设备健康、setup 等字段只有在有权威数据源后才能进入快照。
3. 从事件重算每单完成时间、等待/阻塞、逾期、WIP 峰值及派工次数；同一份事件重复重算结果必须一致，并与 coordinator summary 对齐。
4. 建立固定样本的 FIFO/当前策略基线。此时只评估和报告，不因单次仿真结果改写策略。

**测试与通过门槛：**在 `tests/test_v1_metrics_contract.py` 增加代表性事件序列和 summary 对照；现有指标契约测试通过。若关键数据无法从事件重算，先修事件，不进入策略变更。

### WP2：引入有证据来源的设备状态

**落点：**从 `domain/process_model.py` 的设备目录、`domain/scheduling.py` 的 `DeviceView` 和 `application/coordinator.py` 的设备快照/事件接线增量扩展；测试放在 `tests/test_v1_scheduling.py` 与 `tests/test_v1_coordinator_scheduler.py`。

1. 仅定义首个用例需要的状态（至少区分可接单、忙、故障/停用）；维护状态仅在有实际维护数据源时加入。忙状态继续从活动 execution/resource owner 派生，不复制成可漂移的可变镜像。
2. 状态变更携带来源、仿真时间和诊断证据。未知、过期或来源不明的状态不得视为可接单；生成可追踪的拒绝原因。
3. 静态设备能力仍不能替代目标姿态 IK、碰撞和路径验证；仅使用已通过 focused 仿真的候选组合。

**测试与通过门槛：**覆盖可接单→故障→恢复可接单的合法状态序列、未知状态阻止派工及过期证据拒绝；候选过滤不改变正常 `full_flow` 固定映射。没有有效状态源就不实施本包。

### WP3：只对尚未启动的工序局部改派

**前置：**WP2 通过；至少存在两个语义等价、都已通过 focused 运动验证且被 recipe 明确允许的候选设备。

**落点：**为 `domain/operation_runtime.py` 增加显式 revoke/reselect 生命周期操作；在 `domain/tasks.py`/`application/coordinator.py` 撤销未启动任务队列投影并接回 `domain/scheduling.py`。测试扩展 `tests/test_v1_operation_runtime.py`、`tests/test_v1_coordinator_scheduler.py`。

1. 定义可撤销条件：工序尚未启动、没有 execution ID、未持有物理执行资源、输入物料仍归该工序管理、前驱和配方允许候选未改变。
2. 撤销旧候选选择和 queued task projection；事件记录旧/新设备、故障证据、撤销结果及资源 owner。撤销不改物料账本、不增加 operation attempt。
3. 只对 `PENDING/WAITING` 且满足上述条件的工序重新运行候选筛选。找不到候选时保持可观察的等待或转人工处理，不自动标成功/失败。
4. `RUNNING` 工序禁止通过 scheduler 改派。启动动作失败沿用明确失败/停止语义，不能把已执行的物理副作用当作未执行重放。

**测试与通过门槛：**纯测试覆盖合法改派、启动后拒绝改派、未知设备/不在 allowlist、资源冲突、没有可行替代设备、重复事件不重复 claim；focused 仿真只验证一个选定 arm 工序及其物料提交。随后跑既有 `full_flow` 对照，确认默认决策序列、FINAL 父 UID 和互锁不变。

### WP4：单一故障场景的安全停止与人工恢复边界

**前置：**WP0 已选定故障；明确故障发生时 executor 能否安全停下，并能读取物料 pose、attachment、速度、设备锁存和资源 owner。不能确认现场状态时只允许停机，不允许续作。

**落点：**围绕选定 executor 扩展 `simulation/execution/` 报告字段和 `application/coordinator.py` 的故障收敛；复用 `OperationRuntime.mark_blocked/mark_failed`，必要时再扩展窄状态迁移。新增针对性测试到相应 `tests/test_v1_execution_*.py`、`tests/test_v1_coordinator_*.py`。

1. 将本包故障分类为“未启动”或“执行中”。未启动走 WP3；执行中必须先由 executor 停止并报告现场证据。
2. Coordinator 校验物料 UID/区域/attachment、活动执行、设备安全锁存和资源 owner；将核验结果及失败原因写入事件和实例 evidence。
3. 任一项不一致或未知：保留物料与执行证据，标记 `BLOCKED` 或 `FAILED` 并停止相关作业；不得调用通用 freeze 清理逻辑来代替物理所有权判断，也不得提前释放仍被现场占用的资源。
4. 第一轮人工确认后仍可终止为 `FAILED` 并等待人工处置；不要求自动 checkpoint resume、重试、返工或“复位现场”。

**测试与通过门槛：**对选定故障覆盖安全停止成功、现场核验失败、仿真超时、重复故障报告；证明无重复 UID 消费/产出、无重复 FINAL，资源 owner 与现场占用相符。真实仿真故障注入只在能稳定、可重复触发该故障时进行，否则清楚标成未验收。

### WP5：有边界的恢复策略（条件包）

只有 WP4 证明某个动作可在 checkpoint 安全续作，且业务确实要求自动恢复时才实施。每个工步单独定义 checkpoint、幂等条件、可验证现场条件、最大尝试数及失败后的人工出口。

1. 首先选择无 attach/release 等重复物理副作用的单个工步，定义“动作已发生/未发生/无法判断”的证据判定。
2. 为 runtime 建立显式恢复迁移与 execution ID 关联；恢复只复用同一执行语义，不复用 `mark_resumed()` 作为未经核验的万能入口。
3. 分别测试恢复条件满足、不满足、证据缺失、重复请求和超时。条件不满足时保持停止，不自动改写物料位置或绕过控制器。
4. 返工必须创建新的 OperationInstance 并链接原失败工序；只有出现明确质量返工用例后才实现，不把它作为通用恢复的附带功能。

**通过门槛：**该工步的恢复/拒绝路径均可由事件重放审计；没有这类工步或业务需求时，本包跳过。

### WP6：逐项引入规则调度代价

**前置：**WP1 指标已在固定样本上可重算，WP2 状态数据可用；已有明确业务目标（如降低逾期或等待）。

1. 每轮只增加一个因素，推荐顺序：静态优先级 → waiting aging → due time → 可测的设备队列/处理时长 → 有状态定义的 setup 代价 → 已验证的路线/WIP 代价。
2. 在同一订单集合、seed、工艺候选和仿真工件上比较当前策略与新策略；同时报告完工数、逾期、等待、WIP、重派次数和决策明细。
3. 每次变更提升策略版本；决策必须确定性、可解释，候选最终仍经过本地能力、物料、资源、几何和安全校验。
4. 只有规则策略在固定样本上持续无法满足已写明的目标，才单独评估 CP-SAT/MILP。求解器只产出候选顺序/分配，不能绕过 coordinator 校验。

**测试与通过门槛：**`tests/test_v1_scheduling.py` 覆盖 tie-break、老化边界和不可行候选；coordinator 测试核对事件策略版本与真实派工一致。没有实测收益时保留原规则，不叠加更多代价项。

## 4. 跨包不变量

- Python 仍是唯一仿真时钟；每个 tick 仍由 coordinator 按现有顺序推进，executor 不自行调用 `sim.step()`。
- 一个 UID 同一时刻只有一个物料所有者；工序输出只有验证通过后才提交。FAILED 不能改写成 DONE。
- `ResourceTable` 是资源 owner 唯一来源。未启动任务可以撤销其逻辑预留；运行中资源释放必须结合 executor 停止证据和现场占用判断。
- recipe allowlist 限定候选；能力匹配不代表物理可达。新增设备/路线先做 focused IK、碰撞、路径、负载、结果验证，再开放给调度器。
- CoppeliaSim 写操作只走已有控制器、安全锁存和 coordinator 提交边界；不通过瞬移或直接改账本模拟恢复。
- 不为未来可能的 MES、多 AGV、插件系统、任意用户脚本、在线学习或 UI 配置预建抽象。

## 5. 阶段验收与报告

阶段 5 不以“所有工作包完成”为整体验收；每个启用的包按自身门槛验收，跳过包注明业务原因。至少完成一项明确业务用例后，才可把本阶段标成已实施。

最终报告记录：基线 artifact/digest/seed；实际运行命令与每轮结果；变更的策略版本；派工、资源与恢复事件；物料 UID/父子谱系及终态；事件重算指标；未验证设备/故障组合；失败尝试及其归属。正常基线和故障场景分别报告，不能用一次 `full_flow` 正常通过替代故障恢复证据。

建议检查顺序：

```powershell
python -m pytest -q -p no:cacheprovider
FLEXIBLE_FACTORY_SIM=1 python -m pytest -q tests/test_v1_stage4_scheduler_sim.py -s
```

每个 focused 故障仿真另用独立测试入口和 evidence 文件；只有仿真环境可用时才运行。纯测试通过不能表述为物理恢复通过。

## 6. 暂不纳入

不默认实现全局最优、多 AGV、分布式 MES/PLC、自动现场复位、无上限重试、任意 recipe Python hook、在线学习或对所有故障类型提供通用恢复。后续确有需求时，以一个被证实的输入、消费者和验收目标扩展对应工作包。
