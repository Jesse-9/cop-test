# 项目文档登记表与归档规则

本文是项目文档的分层和对应关系登记表。它解决同一主题同时出现在
`wiki/06-工业案例/柔性车间/` 与 `implementation/` 时的归属问题。

## 1. 归属原则

| 文档层 | 目录 | 回答的问题 | 允许记录的内容 |
|---|---|---|---|
| 项目治理 | `docs/`、仓库根目录 | 项目范围、基线、工程约束是什么 | 范围、决策、基线、全局状态和维护规则 |
| 业务域规划 | `docs/wiki/06-工业案例/柔性车间/` | 业务要建设什么，工艺和对象如何组织 | 场景背景、工艺路线、领域对象、阶段目标、业务验收意图 |
| 技术实施管理 | `docs/implementation/` | 本轮如何落到代码并证明完成 | 工作包、代码落点、测试门槛、实施报告和正式证据 |
| 知识与运行参考 | `docs/wiki/` 其他主题、`98-ProjectUsage/` | 如何理解或运行系统 | 平台知识、模块说明、运行步骤；不替代实施报告 |

`implementation/` 不复制完整的业务规划；业务规划也不记录“已通过”的工程事实。
实施报告是验收事实的唯一权威来源，规划文档只能描述目标、范围和门槛。

## 4. 命名规则

现有编号文件保留，以免破坏历史链接；新增文件按以下规则命名：

- 业务域规划：`06-{序号}-{主题}.md`，frontmatter 使用 `type: plan`、`scope: domain`，标题写清阶段和业务对象。
- 阶段实施方案：`V1_STAGE{阶段}_{主题}_PLAN.md`。
- 阶段实施报告：`V1_STAGE{阶段}_{主题}_REPORT.md`。
- 跨阶段实施方案：`V1_{主题}_PLAN.md`；跨阶段报告使用 `V1_{主题}_REPORT.md`。
- 基线与总报告固定使用 `V1_BASELINE.md`、`V1_REPORT.md`。

同一阶段的“业务规划”和“技术实施方案”使用相同的阶段号与主题词，通过本登记表和
frontmatter 的 `related` 建立对应；不要用两个目录里的同名“方案”互相替代。

## 5. 阅读顺序

1. 先读 `柔性车间/README.md`，确定业务域范围和阶段状态。
2. 再读对应的 `当前规划/06-xx`，了解目标、术语、工艺和业务验收意图。
3. 需要落代码时读 `implementation/V1_STAGE*_..._PLAN.md`。
4. 判断是否完成时只读对应 `..._REPORT.md` 和 `evidence/`，不从规划文档推断实现状态。
